## Contract

The rule is DESIGN Domain "Back-fill", quoted:

> Signals, and the kind each gives (the kind names are the existing closed vocabulary; no kind is added):
>
> | Signal | Where it is read | Kind | Meaning |
> |---|---|---|---|
> | a load of the plan skill: skill id `design` (current), or `plan` (until 15 Sep 2026) or `planning` (until 26 May 2026), with or without a namespace prefix (`yakka:design`, `workflow:plan`) | any point in the transcript | `design` | planning |
> | a load of the `refine` skill | any point | `refine` | refining |
> | a load of the `execute` skill (or its old id `plan-execution`) | any point | `build` | executing a phase |
> | a brief path, `docs/plans/<plan>/briefs/<file>.md` (absolute or relative), in the session's first user prompt | the first user prompt only | `build` | a build worker handed a brief |
>
> The skill id is matched on the part after the last `:`. ... Other skills (`close-out`, `comprehensive-review`, `post-build`, `iterate` and the rest) are not signals: loading one neither labels a session nor makes it multi-signal.

> Signals are counted by signal class (the Meaning column: planning, refining, executing, brief), so loading the same skill twice, or `plan` and `design` in one session, is one signal; `execute` and a brief path are two classes even though both give `build`. A session is **left unlabelled** when it has no signal, or more than one (several workflow skills, or a workflow skill and a brief path). ... An unlabelled session enqueues nothing.

> The plan, phase and issue come from the signal's own text: the skill arguments where the transcript carries them (the Claude `Skill` call's `args`, or the text after a slash command), and the brief path, which names the plan folder and, from the file name `<phase>-<NN>-<slug>.md`, the phase. ... Where those give nothing, the tool's existing subject extraction ... may fill the subject at a lower confidence. ... A session with a single signal but no subject is **not** enqueued ... it is counted as `no_subject` in the report. `confidence` is `1.0` when the subject came from the skill arguments or the brief path and `0.65` when it came from the fallback evidence; no threshold uses it. `evidence` names the signal and where the subject came from, secret-scrubbed, at most 300 characters.

> A harness either gets a recogniser, proven by a fixture built from the shape found, or the report records that no skill-load form was found there (what was inspected and how many transcripts, no content); it then labels by brief path only. The report then shows that harness's skill-based remainder as no-signal, which is what the follow-up review needs to see.

> Discovery skips Claude `subagents/` transcripts (about 361 in the dry run), as it already skips Cursor's. A transcript that a store marks as another session's child is skipped the same way; none is known for Codex or OpenCode.

The count report is DESIGN Domain "Back-fill", quoted:

> The dry run and the real run print, per store (claude, codex, cursor, opencode) and in total: sessions, `labelled` (a single signal and a subject; these are enqueued), and sessions left unlabelled, split by reason: `multi_signal` (more than one signal), `no_signal` (none), `no_subject` (one signal, no subject), `unreadable` (the existing unreadable-transcript and missing-identity rows). `labelled` is also split by signal (planning, refining, executing, brief), so a reader sees how much rests on each. Every discovered session appears in exactly one of those rows. Three counts sit beside the rows so the totals reconcile with discovery: Claude subagent transcripts skipped, transcripts skipped as another session's child in any other store, and duplicate conversation ids (a conversation id seen in two transcript files counts once and enqueues once).

The phase's fixture yardstick is DESIGN Phase 5, quoted:

> Synthetic fixtures for each store the tool reads prove the rule: a session loading only `design` is `design`; only `workflow:plan` is `design`; only `plan` is `design`; only `refine` is `refine`; only `execute` is `build`; a first prompt carrying `docs/plans/<plan>/briefs/<file>.md` and no skill is `build`, with the phase from the file name; the same skill loaded twice is one signal; two different workflow skills, and a skill plus a brief path, are `multi_signal` and produce no label; no signal is `no_signal`; a single signal with no subject is `no_subject` and is not enqueued; a `close-out` or `post-build` load alone is `no_signal`; a Claude `subagents/` transcript is not discovered; and a harness for which the fixture has no skill-load form still labels by brief path; a subject read from the skill arguments gets confidence 1.0, one read from the brief path gets 1.0, and one that only the fallback extraction finds gets 0.65.

Recon findings this brief fixes, so you do not re-derive them:

- **Claude:** a `Skill` tool call is a `tool_use` block whose `name` is `Skill`, with `input.skill` and `input.args` (`tools/quality/interventions.py:48-49`). A `<command-name>` slash command is a user-message line of the form `<command-name>/yakka:execute</command-name>`, with optional `<command-args>...</command-args>`; strip a leading `/` and match the id after the last `:`. Ignore commands that are not signal ids.
- **Cursor:** the `<manually_attached_skills>` block is in a user `text` content block. Its `Skill name <id>` line names each attached skill; match the id after the last `:`. In the 50 real blocks on codyh-ubuntu, 49 carried a `Skill name <id>` line; 17 named non-workflow skills, which are ignored. The block can carry several `Skill name` lines; each is a load.
- **Codex:** no recogniser. Read-only recon on codyh-ubuntu (19 Nov 2026) parsed 2,862 of 2,863 `rollout-*.jsonl` files: 715 `user_message` events, one leading-slash command (`/resume`), no skill tool call; `world_state` holds a `skills` settings dict (`includeInstructions`) and a `host_skills` catalogue, not a load record. OpenCode labels by brief path only; the report records skill loads as unsupported there. The message `agent` field (`build`, `plan`, `explore`) is mode metadata, not a skill load; do not treat it as one.

The first user prompt is not the current `label_session` prompt (the first non-empty line of all concatenated strings; IMPLEMENTATION.md:31). Read it per store from the store's own user-message record:

## Changes

1. **Data model and per-store reads.** Extend `Session` with the actual `first_prompt` and the signals found (a small `Signal` value with signal class, kind, the signal's own text for subject extraction, and source). Keep the existing bounded reads (`1 << 20` bytes, the JSONL head/tail window), `cwd`, `branch`, `files` and `unreadable`. Build the per-store signal list and first prompt from the store's records, not from the concatenated text.
2. **One signal table.** Put the id table in one place: after the last `:`, `design`/`plan`/`planning` → class planning, kind `design`; `refine` → class refining, kind `refine`; `execute`/`plan-execution` → class executing, kind `build`. Everything else is ignored. Claude `Skill` and `<command-name>` and Cursor `Skill name` all use this table. Add the brief-path recogniser separately: `docs/plans/<plan>/briefs/<file>.md`, absolute or relative, in the first user prompt only → class brief, kind `build`, plan from the folder and phase from the leading integer of `<file>` when it is `<phase>-<NN>-<slug>.md`.
3. **Count classes, not loads.** Collapse repeats by class (`plan` + `design` is one; the same skill twice is one); two different classes are `multi_signal` even when both give `build` (execute + brief path). A signal is a load anywhere in the transcript for the three skill families; the brief path is the first prompt only.
4. **Statuses and subject.** Use `labelled` (one class and a subject), `multi_signal`, `no_signal`, `no_subject`, `unreadable` (the existing unreadable transcript plus the existing missing Codex identity). `labelled` carries the kind and action; the other statuses carry no action and enqueue nothing. Subject: plan/issue from the signal's own text (skill args or command args; brief path gives plan and phase) at confidence 1.0; the existing `PLAN_RE`, `PHASE_RE`, issue/PR extraction over the existing haystack (text, cwd, branch, files) may fill only a missing subject at 0.65. `--repo` is still required for a plan or issue subject. PR alone is not a subject. Evidence names the signal and the subject source (for example `signal:cursor_block:execute; subject:fallback`), not a prompt snippet; run it through `_scrub_evidence` and keep it under 300 characters.
5. **Discovery and counts.** Skip Claude `subagents/` transcripts as Cursor already skips its own, and count them: Claude skipped transcripts are `skipped_subagent`; Cursor skipped transcripts are `skipped_child`. Count duplicate conversation ids: a conversation id seen in two transcript files is one session row, counted once in `sessions` and enqueued at most once; print the duplicate-id count and the number of extra transcripts it removed so discovery reconciles. Return the discovery counts to `main`.
6. **Count report.** Print per store (`claude`, `codex`, `cursor`, `opencode`) and `total`: `sessions`, `labelled`, `multi_signal`, `no_signal`, `no_subject`, `unreadable`, and `labelled_by_signal` split into `planning`, `refining`, `executing`, `brief`. Beside them print `skipped_subagent`, `skipped_child`, `duplicate_ids`, the `duplicate_transcripts` removed, and `transcripts_discovered` per store and in total, so the report can show `sessions == labelled + multi_signal + no_signal + no_subject + unreadable`, `labelled == sum(labelled_by_signal.values())`, and `transcripts_discovered == sessions + skipped_subagent + skipped_child + duplicate_transcripts`. Keep the offline `--server-fact-count` and `--server-action-ids` options as they are; they make no request.
7. **Enqueue.** Enqueue only `labelled` labels (a single signal and a subject), at most one per conversation id, through the unchanged `yakka.EnqueueSessionAction`; leave `Build` unchanged. `no_subject` and every other unlabelled status enqueue nothing. Keep the local label file, the dry-run default and secret scrubbing.
8. **Remove.** Delete `QUEUE_FILE_RE`, `parse_queue_logs`, `--queue-logs`, queue truth in `label_session`; delete `score_gold`, the gold fields of the result and the gold tests; delete `FLASH_RE`, `is_flash_analysis`, the OpenCode-only Flash gate and the `excluded` status; delete the 0.55 tier.

## Solution Shape

Extend the existing shared REST/MCP review orchestrator and tenant stores. The server owns schemas, call policy, findings, paging and spend; the shim continues bounded local collection only. General effort/tags/store parameters replace trial capability gating. Persisted synthetic activity runs on the real deployed server under a dedicated tenant/key; `store=false` serves secondary ephemeral use. Add human-owner self-serve reset (retain identity/ownership) and delete (erase identity too), both through the web UI only, with complete tenant/global asset cleanup. Trial tooling verifies full history, uses complete filtered reads and keeps explicit paid-spend authorization separate from zero-call preflight.

### Domain: review call and cached response (Decisions 3–6)

Owner: `internal/review`, REST `POST /v1/reviews`, server-defined MCP `review_change`, `internal/store`/`internal/ingest`. Both transports share validation, response fields and effects. Existing capture, criteria, disclosure checks, fixed provider endpoint, bounded retries, non-gating workflow use and `read_write` authorization remain in force, including for unpersisted spend.

| Optional argument | Contract |
| --- | --- |
| `effort` | Omitted means `high`; exact strings `high`, `xhigh`, `max` only. Null, empty, other values and wrong types are argument errors before spend or storage. Valid for any supported review mode; neither trial identity nor a deployment toggle is required. Persist configured effort (`high`), requested effort (including default resolution) and effective effort; send effective effort explicitly on every provider attempt. |
| `tags` | Omitted means `[]`. At most 16 strings, each 1–96 ASCII bytes matching `[A-Za-z0-9][A-Za-z0-9._:/=-]{0,95}`; case-sensitive. Reject wrong types/null, controls, whitespace, invalid charset, overlength or overcount before effects. Count the submitted list before deduplicating; canonicalize accepted values as a sorted unique set. Apply existing metadata disclosure checks; tags are visible metadata, never provider prompt content. |
| `store` | Boolean, omitted means `true`; null/wrong types rejected. `false` returns full validated review data, never writes review records, captured inputs or findings and never enters list/search/quality pathways. Skip **all dedupe/cache reads and writes**, including persistent execution claims. Each explicit call is independent paid work if it reaches the provider; transport ambiguity must never cause an automatic replay. |

`YAKKA_REVIEW_TRIAL_ENABLED` is dropped entirely: remove its config field, env parsing, availability branch, documentation and fixture expectations. It meant “permit historical trial effort overrides”; per-call validated effort now does that job and stored effort makes overrides auditable. `YAKKA_REVIEW_EFFORT` remains a high-only server default/validation setting; it never limits a valid per-call override. `YAKKA_REVIEW_MODEL` stays server-only and must equal `claude-haiku-5-5`; no client model parameter. Configured/returned reviewer ids remain recorded. No live provider capability is claimed by this amendment.

For `/v1` additive compatibility, old `trial{manifest_hash,case_id,effort}` remains only as a deprecated input adapter, with its existing syntax/range validation but **no env gate**. It translates to the same effort and general tags, preserves legacy manifest/case/profile read fields and can resolve old execution claims. Top-level effort plus a conflicting legacy effort is an argument error; equal values are accepted. The adapter generates `effort:<level>`, `manifest:<hash>` and `case:<sha256-of-case-id>` tags, unions them with caller tags, and validates both the submitted and merged sets against the same bounds. Original cached legacy records remain immutable and untagged; a compatibility duplicate audit row may carry these mapped tags and the canonical pointer. New clients never send `trial` or a special run/label argument. Old stored records and all old read filters remain readable; absent tags mean an empty set. Effort/tags/store are sufficient for new requests. Legacy identity is not a prerequisite for any effort.

For `store=true`, lookup the original review by tenant and execution key directly, without a 500-row scan. Execution identity keeps capture, criteria, build models, reviewer model, effective effort and policy/ordinary review identity. For ordinary requests with an empty canonical tag set, preserve the exact pre-upgrade execution-key serialization/hash, including its ordinary profile, so existing untagged paid work remains cached after upgrade. Nonempty tag sets use a distinct versioned key containing the canonical set, so independently tagged experiments remain distinct; they never collide with untagged keys. Legacy-key fallback is allowed only for a legacy-adapter request whose canonical merged tag set equals exactly the three deterministic adapter tags (no extra caller tag), with matching stored legacy manifest/case/effort and every other old identity field. A request with any additional tag uses only the new tag-sensitive key and must not fall back to a legacy key. New requests without the legacy object never use this fallback. A cache hit returns the **full cached review in the fresh response shape**, even when `detail` is omitted/receipt: `status=skipped_duplicate`, `cached=true`, `original_review_id`, and `original_status`, with original result, coverage, finding counts, model/effort, tags, attempts and usage/cost evidence. `reason` remains the original id for old clients. Original payload/status are never misrepresented as a new successful review; no new provider cost is incurred. Fresh default receipts retain their existing size; `detail=full` gives their full review. `store=false` always gives full review regardless of detail. Captured content is never returned.

A claim whose original request is still running or whose provider outcome is unknown cannot invent a cached review. Return `in_progress` or `outcome_unknown` with original id and `cached=false`, no result, no second provider call; reserve `skipped_duplicate` for a completed stored original, including stored terminal errors whose result may be absent. Missing/corrupt originals fail explicitly (`cache_unavailable`), never become an empty successful cache hit. Completed duplicate responses have REST/MCP parity in every payload field. This replaces the old Phase 5 reference-only parity interpretation; it does not reopen Phase 5.

Zero-call refusals do not consume execution claims. Stored duplicate audit rows may remain for compatibility, but are marked as references with no new attempts or charge; reports count the canonical original once. A returned original's historical cost is evidence, never incremental duplicate spend. Changing effort creates independent identity. Concurrent equal stored calls and restarts preserve the original claim.

For `store=false`, keep only a **content-free `review_usage` fact in the caller's tenant**, outside `review_run` and quality/conversation/hook/facet aggregates: random usage id, configured/returned model, configured/requested/effective effort, tokens, estimated cost/pricing identity, timestamp, validated tags, `store=false`, attempt/status and unresolved-reservation accounting. No repo/plan/session/capture identity, prompt, criteria, findings, error bodies or content-derived hashes. It enters an explicitly named tenant review-spend measure, never work_cost or quality counts. Synthetic callers use the synthetic key even for these facts. Spend reservations/in-flight limits still apply under fresh non-cache identifiers, attributed to the tenant, with conservative charge for unknown outcomes. `dry_run` writes none of these facts or reservations and makes zero provider calls; it wins over store/detail and validates configuration, allowlist, effort and disclosure readiness first.

### Domain: complete tenant-bound reads (Decisions 1 and 5)

Owner: REST GET reviews, new server-defined MCP `list_reviews` (read scope, read-only, no local readers/actions), store review queries. The shim learns the tool through the registry; no tool-name/schema logic is added to the client.

Both entries accept the existing repo_id/plan/phase/kind/status/effort/profile/manifest_hash/since filters, `detail=full`, `limit` and `cursor`; add exact tag filtering: repeated REST `tag=value`, MCP `tags:[value,...]`, with the same 16 × 96 bounds. Multiple tags mean **ALL**, conjunctive with all other fields. An empty filter matches all tenant reviews, including old untagged records; a tag filter never matches an untagged record. Invalid filters return an explicit argument error. Preserve the existing REST `reviews` array and add `next_cursor` (opaque string or null) and `complete` (boolean); MCP returns the same data object. Limit is page size (default 100, range 1–500), never a complete-read ceiling. Other analytics endpoints retain their limits.

The first page fixes an insertion high-water mark in the tenant review store; subsequent pages use stable descending `(ts, insertion_id)` ordering with a strict last-key boundary, never offsets. Bind cursor version, authenticated tenant, route, canonical filters, detail and high-water mark. A cursor cannot select or authorize another tenant. Malformed, mismatched or unsupported cursors fail explicitly (REST 400 / MCP invalid arguments); after reset they cannot revive a tenant. Page size may change without changing selection. Rows appended later, including backdated ts rows, cannot enter the fixed read. Existing review rows and tags are immutable during this walk. A reset or store generation change invalidates the walk rather than silently dropping rows.

Every nonterminal page has `complete=false` and a progressing cursor; the exhausted page has `complete=true,next_cursor=null`, including exact-multiple and empty populations. A decode/query/corrupt-row error fails the page; do not silently skip malformed stored review rows. No source row can be silently omitted. Consumers verify protocol consistency and unique row identities; cycles, missing completion metadata, request failures, early interruption or an operator safety ceiling produce a nonzero/incomplete result, never a complete report. Saved trial exports carry filters, high-water identity, exhausted-page evidence and counts; a legacy bare 500-row response cannot certify completeness. No fixed total row ceiling is substituted for paging.

Owner: existing registry/auth/tenant lifecycle, store manager and review reservations own authorization and erasure; the profile UI owns human confirmation and selection invalidation. The real deployed Yakka server remains the trial target; its provider credential stays server-side. Trial review tooling uses a dedicated Yakka `wk_` key. That key never authorizes reset/delete.

Record the immutable tenant id, not just its name. Add `<synthetic-tenant-id>/<repo_id>` to `YAKKA_REVIEW_REPOS` through normal operator configuration. Confirm the key's identity with whoami before any capture; abort a real-work mismatch. Provisioning, configuration, deployment and token handling remain later operator acts.

Synthetic reviews use `store=true`: tags, caching, paging, tracking and costs work normally within that tenant. A real-work bearer or its selected owner-session tenant sees none of the synthetic reviews, findings, search, usage, analytics or costs. Shared owner identity never combines tenants. There is **no separate synthetic-spend counter**. The provider-wide rolling safety cap remains an operational shared budget, never a tenant analytics source or permission to reveal another tenant's spend.

Raw directory removal leaves registry tokens/owners and global reservations/claims; valid tokens can recreate storage. Sessions are user-global. The selected tenant is browser state plus `?tenant=`, not a field in the session record. The merged #218 admin-reset text was a pending contract, not shipped behavior.

**Endpoint descriptions — pending Phase 2:** Only the human owner may reset or delete a tenant. Agents must not perform or attempt this on a user's behalf. Replace the proposed `/v1/admin/tenants/<tenant-id>/reset`; no admin reset alias, redirect or fallback is introduced. These remote-only routes authorize against the path tenant's registry owner, never an admin flag, display name, selected tenant or key scope:

| Method and path | Required body | Successful result |
| --- | --- | --- |
| `POST /v1/tenants/<tenant-id>/reset` | JSON `{"confirm_tenant_id":"<exact path id>"}` | `204` after erasing every tenant asset except the immutable tenant id, display name, owner link and trustworthy lifecycle marker; retain an empty reusable tenant with a new store generation. Revoke/remove every old token and grant; the owner must issue a new key before reuse. |
| `DELETE /v1/tenants/<tenant-id>` | Same required JSON confirmation | `204` only after removing the tenant entirely: identity/name/owner/marker, tokens, tenant-bound sessions if any, all data and attributed global state, and cleanup journal. Future experiments require a new tenant id/key. |

Both routes require **all** of the following before effects: a valid browser `workflow_session` cookie for the owner; exact `Origin` equal to the configured public API origin (reject absent, `null`, malformed or other origins); `Sec-Fetch-Site`, when present, equal to `same-origin`; fixed dedicated header **`X-Yakka-UI: tenant-lifecycle`**; `Content-Type: application/json`; and a nonempty string `confirm_tenant_id` exactly equal to the immutable path id. Do not accept `same-site` as `same-origin`. This tightens the existing admin JSON/Origin pattern for these routes only; the broader Pages/configured CORS allowlist does not grant lifecycle permission. If **any Authorization header or other API-key/token credential is supplied**, reject before cookie fallback, including invalid/expired keys and bearer + valid owner cookie + valid UI headers. No key-authenticated caller succeeds. Local keyless mode is also refused. There is **no MCP reset/delete tool** or CLI/runner lifecycle command; guessed tool calls remain unknown-tool errors without effects.

Validation/error ordering is part of the contract. Reject key/token credentials first with `403 tenant_lifecycle_ui_only`, with JSON `{"error":"tenant_lifecycle_ui_only","message":"Only the human owner may reset or delete a tenant. Agents must not perform or attempt this on a user's behalf. Open the profile UI."}`; local mode returns the same. A cookie-only request without a valid session returns `401 session_required` and a sign-in hint. Next reject Origin/Fetch-Site/UI-header failures with `403 tenant_lifecycle_ui_only`; reject non-JSON with `415 json_required`. For a valid UI session return `404 tenant_not_found` for absent ids and `403 tenant_owner_required` for any existing tenant not owned by that session, including an admin non-owner. Then malformed JSON/missing/wrong-type/mismatched confirmation returns `400 tenant_confirmation_mismatch`. Next legacy tenants without a trustworthy creation/ownership marker return `409 legacy_tenant_cleanup_unsupported`. All these refusals precede lifecycle locks, journals, lazy-open, spend, selection changes or destructive work; malformed/unknown ids never open storage. A repeated delete of an absent id is `404`, with no tombstone or ownership bypass; a reset of an absent id is also `404`. A repeated confirmed reset of an existing eligible tenant wipes its then-current assets again; it never silently returns a cached earlier success.

**Profile UI and selected tenant:** Both actions may target the session's currently selected owned tenant, including its only tenant, with the same explicit id confirmation. The modal names the action, display name and immutable id, requires the user to type that id, and includes: **“Only the human owner may reset or delete a tenant. Agents must not perform or attempt this on a user's behalf.”** Reset copy adds “Erase all tenant data and revoke its keys. Keep this tenant and your ownership; issue a new key to reuse it.” Delete copy adds “Permanently remove this tenant, all its data and keys, and your ownership link.” Cancellation or any rejection leaves data and selection unchanged. After either `204`, clear target selections, cached tenant reads and cursors in the acting UI origin (and notify its same-origin tabs); reload `/v1/me`, stay on profile and require explicit re-selection or creation, without automatically choosing a fallback even if only one tenant remains. Any server-side tenant-selection references must also be cleared. Preserve user-global login and other owned tenants. Deleting the final tenant does not recreate one during cleanup; existing later OAuth login may provision a fresh default under a new id. Other origins/browsers revalidate stale selections as described below; deleted ids fail ownership, reset ids invalidate old generation cursors/cache. A lost/non-success response never implies success; refresh the owner lifecycle state below before offering any fresh confirmed retry, never automatically replay the destructive request.

**Read-only recovery and cross-origin selection:** Phase 2 additively extends each owned tenant in `GET /v1/me` with `lifecycle_state` (`active`, `resetting`, `deleting`, `unsupported`) and `lifecycle_generation` (opaque string for ownership-marked tenants, null for unsupported legacy). During cleanup, the owner's entry remains visible with its in-progress state; recovery authorization/identity metadata is retained until the final boundary. Completed reset becomes active with a different generation; completed delete disappears from the owned list. Read these fields from registry/journal metadata only, without lazy-opening tenant storage. Disable lifecycle confirmations while resetting/deleting or while recovery reads fail; after recovery any subsequent mutation requires fresh typed confirmation. This lets the profile distinguish pending work from completed reset/absence without replaying a mutation. On ambiguous response, show the observed state or “completion unknown” if the read fails; do not claim a successful receipt from uncertainty.

API-origin and Pages UI origins have separate localStorage. They cannot erase each other's browser state directly. Both must revalidate `/v1/me` on profile return, focus/pageshow and before issuing tenant data reads, compare the selected id/generation and clear selection/cached reads/cursors when the id is absent or generation changed. In-progress state suspends target reads and confirmation until recovery completes. Suppress existing automatic-first-tenant fallback after invalidation, including with one remaining tenant. Same-origin tabs receive invalidation notifications; Pages or another browser observes it at its next validation before showing/issuing tenant data reads. No cross-origin message grants authority or carries credentials. Existing unrelated legacy selection behavior is retained. These are profile/selection changes, not an analytics redesign.

The lifecycle view must be served at the **API origin**, including the production collector where the current image lacks the analytics bundle. Phase 2 supplies the bounded profile lifecycle view there; a Pages profile links the human to that view by navigation. Do not relax the lifecycle gate for Pages, proxy a key-authenticated call or depend on paused analytics work. Existing OAuth callback, other UI routes and general CORS behavior retain their contracts. No deployment is authorized by this amendment.

Both operations block target admission, token issuance/device redemption and background writes before erasure; drain/cancel in-flight reviews and wait for final reservation settlement; stop screening/rescore/queues; close readers/writer/WAL/locks; evict store/claim/read caches. Erase the full tenant directory (facts, reviews, findings, captures, tags, usage, rollups, blobs, pending, archive, review-inputs and temporary files), every registry token including revoked/expired entries, approved device grants, attributed claims/reservations, tenant-bound sessions if any, and selection references.

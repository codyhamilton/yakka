## Problem

An agent that writes a design and calls `artifact_feedback` has never received `delivered` with a verdict and scores, so it cannot act on a flagged check or record a pass. Each cause below was traced in the code and against live evidence; none is a single bug.

1. **The final write is invisible to capture.** The client learns a file changed only from a PostToolUse event whose `tool_name` is in a fixed write-tool set (Write, Edit, MultiEdit, apply_patch and a few aliases; `_write_tools` in `plugins/yakka/client/yakka.py`). The budget session `c70d3e4f` wrote `docs/plans/01-local-finance/DESIGN.md` three times with Edit (02:03:58-02:04:00Z), then a last time with a Bash `python3 - <<'E' ... open(p,'w')` heredoc at 02:04:06Z, the 1 s gap in the issue. The remote's hash received at 02:04:05Z is the Edit-era content. The Bash call produced a hook event but no `artifact_version`, because a shell command names no path the client can attribute. Nothing else rescued it: the commit catch-up (design 01) sends the committed blob only from a captured `git commit` tool call, and the transcript has none (commit 52435db appears between sessions), and the Stop hook at 02:04:15Z carries no paths. The remote never gets the final hash and `artifact_feedback` returns `stale`, whose message ("normally a write still in the batch window") tells the agent to wait for something that never arrives. This account is from the session transcript and is consistent with the code; the budget checkout itself was not read. The drain is sound: it reads content at batch time, has no per-write debounce, rescans after releasing its lock (no lost wake-up), and the server returns the latest version by `received_at`.
2. **Secret-scan withholding is silent unless the file is matched.** The client withholds an `artifact_version` whose content hits a pattern, for worktree writes and for the commit catch-up, and moves the queue file to `queue/rejected/` with a `.reason`. The live yakka queue holds five such files (`env_assignment` at line 40 of a brief and at line 775 of `docs/plans/91-landing-centered-dial/DESIGN.md`). A long design that trips the scanner is never delivered. This is a second way a version fails to reach the remote, with the same fix surface; the scanner's patterns are not changed here (open question 2).
3. **`delivered` does not say whether the file was scored, and the scorer state is not surfaced.** The server screens in a worker and scores only when a scorer and a checks directory are configured: no `TYPESAFE_API_KEY` yields "scorer none; verdicts are unscreened", and a key without `YAKKA_CHECKS_DIR` yields "scoring is off ... screening only" (`packages/yakka/cmd/yakka/main.go`, `runServe` startup via `screenStep`). Today the local feedback handler prints `screen: unscreened (no scorer on the service)` and `screen: awaiting screen` (`plugins/yakka/client/yakka.py`, `screen:` lines at 2129-2146), but it cannot tell the agent whether "awaiting" means seconds or never, and content stored while the scorer was off stays unscreened until an admin rescore (#169). Whether the live remote has the scorer on could not be established from this checkout and cannot be changed in this run; the service knows it (`scoring()` in `packages/yakka/internal/serve/admin.go:89-92`, today exposed only through `GET /v1/admin/status`), so the build reads it first.
4. **Codex never calls feedback, for two reasons.** The Yakka MCP is loaded in Codex (`codex mcp list` shows `yakka`, enabled, `python3 ./client/yakka.py mcp`), so loading is not the gap (the issue's "may not be loaded" is answered). First, the instruction to call feedback lives only in the design, refine and execute skills; no Codex session after the switch from the old `workflow` plugin (about 2026-10-31 08:30) read a skill or made an MCP call. The issue says Codex AGENTS.md carries the instruction; the files inspected (no `~/.codex/AGENTS.md`; the budget and garcia-music project AGENTS.md) contain no Yakka or feedback text, so the instruction as shipped does not reach Codex. Second, `.codex-mcp.json` sets `"cwd": "."`, so the server runs in the plugin cache root; the nine historic Codex calls (all to the old `mcp__workflow__` tool) failed on relative paths resolved under `~/.codex/plugins/cache/...` and, with absolute paths, returned `not delivered`. The same relative-path trap applies to the local Yakka MCP process today: it resolves a relative path against its own `os.getcwd()` and reads no harness project-directory variable or MCP roots (`yakka.py:1875-1880`, `1971-1977`). The MCP `instructions` string describes the tools and does not tell the agent when to call them.
5. **A local fallback exists in the client, and tests encode it.** `LocalEndpoint = "http://127.0.0.1:8770"` is substituted when no client config exists (`Load()` in `plugins/yakka/client/yakka.py`), and `yakka status` prints "config: none (local mode)". There is no explicit local marker, so a client with remote intent but no file fails over silently. The Oct 30 `unreachable` results came from this path, because `client.toml` did not exist until 2026-10-30 23:37 AEST; that file now exists, so this machine is safe by accident. Half-set env is already an error and no code substitutes the local endpoint after a failed request; the gap is the file-absent and no-marker cases. Python tests that assert the old behaviour (`TestMissingFile` in `test_clientconfig.py`, `test_status.py`, and any other that relies on the no-file default) will change. The Python `login` default (`https://api.yakka.build`) differs from the runtime default.
6. **A legacy process still runs, and a backlog is stranded.** pid 7649, `~/.cache/workflow/0.1.0/workflow-linux-amd64 mcp`, is the MCP child of a long-lived `codex` started by `~/.config/systemd/user/codex-usage-probe.service` (tmux server `codex-usage`, a `while :; do codex ...; sleep 15; done` loop). That codex predates the switch to the `yakka` plugin and loaded the old `workflow` plugin copy at `~/.codex/plugins/cache/workflow-plugin/workflow/2.9.2/`. `~/.config/workflow/client.toml.bak-pre-local` still holds a 127.0.0.1:8770 endpoint and a key. `~/.local/share/workflow/queue` holds 37,931 unsent `*.evt` files (167,853,844 bytes, 2026-10-23 to 2026-10-31; all Codex hook events) plus 38 rejected entries; nothing reads that directory. A successful drain deletes what it sends, so draining it in place is destructive and cannot be retried.
7. **All MCP tool logic is in the local client, and the server has no MCP endpoint.** The `# --- mcp ---` section of `yakka.py` (lines 1840-2514) holds the tool list, descriptions, schemas, `readOnlyHint` annotations, `_MCP_INSTRUCTIONS`, argument validation and every `artifact_feedback` state and wording; the Go server registers REST routes only (`internal/serve/serve.go:485-523`). Items 1, 3 and 4 each land in that section: the feedback wording, the `stale` and scoring states, the instruction text, relative-path resolution and the read-only annotation. `artifact_feedback` also reads cwd, stat and file bytes (hash), `git rev-parse --show-toplevel`, git remote or root commit (`repo_id`), a scan of the queue directory for unsent writes of the file, the drain lock, `Load()`, and starts the drain (`yakka.py:1967-2063`). A decision of 2 Nov 2026 makes the local MCP side a thin shim and puts all tool definitions and logic on the server; a separate Yakka issue, the MCP shim issue (#177), builds that, and this design depends on it.

## Solution Shape

After this change, a client either talks to the remote it was configured for or stops with a message; every changed design, brief or report reaches the remote whichever process wrote it, always through the local queue and the drain; `artifact_feedback` is read-only on the service, says whether the service holds the file's current version, and when it does not, has the shim queue the file for the drain (a secondary effect, decided by Cody, 2 Nov 2026, 11:18 PM AEST) and answers "queued, call again" at once; once delivered it says exactly what the service did with the file (screened and scored, scoring off, or still pending); both harnesses tell the agent to ask for feedback and Codex resolves paths correctly. The legacy source is retired and the stranded history is uploaded once through the same pipeline. Every MCP tool this plan adds or changes is defined and answered on the server; the local shim forwards the call with auth and local context added and, when the server asks, runs one named local effect and forwards again.

### Domain: Client configuration (endpoint resolution)

- Owns: deciding remote, explicit local, or a named error from env and `client.toml`; the wording of config errors; the Python client (`plugins/yakka/client/yakka.py`) as the one implementation; the `yakka status`, Python drain and MCP shim consumers of that decision (the shim takes its endpoint and bearer from `Resolve`, the one login the drain also uses).
- Contract: `Resolve` returns exactly one of `Remote{endpoint, key}`, `Local` (loopback endpoint `http://127.0.0.1:8770`, no bearer) or `Error{what, fix}`. First match wins:
  1. `YAKKA_ENDPOINT` and `YAKKA_KEY` both set: Remote with those values. `YAKKA_MODE=local` alongside either is an Error (conflicting).
  2. Exactly one of the two set: Error (`what`: which is missing; `fix`: set both or unset both). This already exists.
  3. `YAKKA_MODE=local`, neither set: Local. The env form overrides the file for processes that inherit it.
  4. `client.toml` (path `YAKKA_CLIENT_CONFIG`, else `~/.config/yakka/client.toml`) present: `mode = "local"` with no key is Local; `endpoint` and `key` both present is Remote; anything else (key without endpoint, endpoint without key, `mode = "local"` with a key, unreadable or unparseable file) is an Error naming the file and the field. The file is the primary marker because harness-spawned hook, shim and drain processes do not inherit a shell variable set only for `yakka serve`.
  5. Nothing set and no file: Error "yakka is not logged in", fix "run /yakka:login, or set YAKKA_ENDPOINT and YAKKA_KEY, or set `mode = "local"` in client.toml for a local server".
  A resolved Remote is used as configured for every request in the process; no path substitutes another endpoint on failure, partial config or absence. `127.0.0.1:8770` appears only as the Local endpoint and as the `yakka serve` bind default. Local mode is the Python drain posting over HTTP to a loopback `yakka serve` (which ignores bearer tokens, so no key is sent); no part of it relies on `yakka serve` hosting the drain.
- Failure contract: a failed remote request reports what failed (network, auth, server status) against the configured endpoint with userinfo stripped, says whether events stay queued for retry, and gives the fix (`yakka status`, `/yakka:login`, network). Hooks still spool with no network and never fail the agent. A drain whose config is an Error leaves queued files untouched and logs the error once. The shim's failure is its own error, not a tool state: when `Resolve` is an Error, or the server cannot be reached, the shim answers the forwarded request with an error that begins `bad config` or `unreachable`, names what failed, says how many local writes stay queued, and gives the fix. Those two cases stay in the shim because they are how it reaches the server; no tool wording or state lives there.
- Non-goals: the server's own `Config.Local()` (server-side local mode), the sync credential of plan 18 (it already refuses loopback), the login OAuth flow.

### Domain: MCP boundary (local shim and server surface)

Owned by the MCP shim issue (#177), which builds the generic mechanism: the server's declaration of named context and of permitted local actions, the shim's forwarding, injection and directive handling, the endpoint. This design relies on it and adds one thing to what #177's rule says (ledger 22, open question 6): besides auth and local context, the shim runs a named local effect the server asks for. Plan 21 phase 3 owns the readers for the names the Feedback tool declares (`project_dir`, `cwd`, `file`, `git`, `queue`, `drain`, `effects`, the base-list resolution for `resolved_path`), the one local action it declares (`enqueue_file_snapshot`) and the server tool that declares them; the shim reads and runs only what a declaration names.

- Owns: the split between the local MCP shim in `yakka.py` and the MCP endpoint on the Go server.
- Contract: the shim does three things and nothing else. (a) It injects auth: the bearer key from `Resolve`, the one login the drain also uses (no bearer in explicit local mode). (b) It injects local context: values only readable on the agent's machine, added to the forwarded call as parameters. (c) It runs a server-requested local action, a generic mechanism with no per-tool code: a tool definition declares `local_actions`, a list of action names; a reply to `tools/call` may carry a machine-readable directive `{action, path}` instead of an answer; if `action` is in that tool's declared list and `path` equals the `resolved_path` the call already carried, the shim runs the action, re-reads the declared context, adds an `effects` entry `{action, ok, error}` (`error` a code, never wording), forwards the same call once more, and relays that second reply unchanged. The directive reply and its text are never shown to the agent. The shim runs at most one directive round per call. An action not in the declared list, or one the shim has no implementation for, is not run: the shim forwards once with `effects` `[{action, ok: false, error: "unsupported"}]` and the server words it. A second directive in the second reply is neither run nor relayed: the shim answers with its own error beginning `bad directive` that names the action. The actions are a fixed table of generic local mechanisms in the shim (today one), not per-tool code. Everything the shim adds rides under one reserved key (`_local`) that it overwrites, so the agent cannot supply `file`, `queue`, `effects` or any other context; the server reads only that key. The shim decides nothing about when an action is needed. It forwards `initialize`, `tools/list` and `tools/call` to the server's MCP endpoint and relays the replies unchanged otherwise. It holds no tool list, descriptions, schemas, `instructions`, argument validation, state logic or wording. Which context and which actions each tool gets is declared by the server in its tool definition, never hard-coded per tool in the shim. Every tool definition and its logic live on the server.
- Stays local: config resolution (Client configuration domain), the no-local-fallback error, the shim's own `bad config` and `unreachable` errors (they are how the shim reaches the server), hooks, the spool and the drain. The drain stays a separate local piece; the shim's one action only adds a file to the queue the drain already reads and makes sure a drain is running.
- Non-goals: moving `list_checks` and `search_artifacts` or building the endpoint (the MCP shim issue); any tool logic in `yakka.py`; any write to the service by a Plan 21 MCP tool (`artifact_feedback` posts nothing).

### Domain: Artifact capture (worktree to remote)

- Owns: which file versions are sent and when; client-side secret withholding; reconciliation of local content against the remote.
- Contract: every worktree `artifact_version` for a scored-kind file in a git work tree reaches the service the one way, through the local queue and the Python drain, and two triggers put a file there. The queue entry is a new kind, `artifact_snapshot`: one `.evt` file in the form the spool produces (written under `tmp/` then renamed, named `<conversation_id>-<ts>-<pid>-<rand>.evt`, one JSON envelope line `{"ts","harness","event":"artifact_snapshot"}` then a JSON payload carrying `session_id` `feedback-<repo_id>`, `cwd` (the repo top) and the file's absolute `path`). It holds a pointer, not the content: like every worktree write today, the drain reads the file at batch time (`_read_file`, `yakka.py:658-668`), so a file changed between enqueue and drain is sent in its newer form. The build's drain turns the entry into one `artifact_version` (source `worktree`, `conversation_id` `feedback-<repo_id>`, `ts` the file's mtime, a build change: today a fact's `ts` is the envelope's, the enqueue time) and no `hook_event`, through the existing scan, hash and conversation-ID rules, and the queue matchers (`_write_paths`, the `queue` context) recognise the kind. The drain is the sole eligibility gate: it resolves the real path before the repo and kind test, and an entry that yields no `artifact_version` (not UTF-8, outside the repo or a symlink out of it, not a scored kind, no repo identity) is moved to `queue/rejected/` with a `.reason` (`unreadable`, `not_in_repo`, `not_scored_kind`) instead of being deleted silently, so no call can loop on an entry that vanishes without a version. (a) `artifact_feedback`, as the secondary effect: the server compares the injected `file.content_hash` with its latest hash for `(git.repo_id, git.rel_path)` (`Tenant.Artifact`, `store.go:929-938`). If they are equal it answers from the service's data. If they differ or no version exists, and the injected `queue` shows no covering entry (a pending entry whose `mtime` is at or after `file.mtime`; an older entry may have been read by a batch before the last write) and no rejected entry at or after `file.mtime`, the server replies with a directive `enqueue_file_snapshot` for the call's `resolved_path` and takes no other action; the shim enqueues the `artifact_snapshot` (through `spool.sh`, ledger 23, so the form is the spool's and the drain kick is the spool's: a drain is started unless one holds `.drain.lock`; `spool.sh` gains one opt-in line, `YAKKA_SPOOL_PRINT=1` prints the queue file name, so the shim can tell queued from dropped) and forwards the call again with `effects` and the refreshed `queue` and `drain`; the server then answers `queued`, naming the pending entry, whether a drain is running and that the agent should call again shortly. If the version is already pending on the queue, from a hook, a Stop sweep or an earlier call, no directive is sent and the call returns `queued` at once. The call never waits for the drain, never posts the file and the MCP route never carries file content: the service receives the version only from the drain over `/v1/ingest`. (b) The Stop and SessionEnd events (the Claude and Codex hook files both have them), local and in Python: for each scored-kind file that `git status --porcelain --untracked-files=all` reports modified or untracked in the session's working repo (untracked directories are expanded to files), an `artifact_snapshot` entry is written in the same form. `spool.sh` is unchanged for hooks (bash builtins, no parsing, no network, no Python; only the opt-in print above is added); the sweep runs in `yakka.py`, either on the Stop and SessionEnd hook events the drain reads from the queue or in a hook command the plugin adds, which the build settles. No client-side "last sent" memory exists. The service's row hash covers every top-level key except `id` and `content` (`internal/keys/keys.go` `Canonical`, so `type`, `ts`, `conversation_id`, `repo_id`, `path`, `content_hash`, `source`, `harness` and `event` all count), so a repeat of unchanged content from the same conversation and mtime is answered `duplicate`; a re-touched file with the same content stores one more row, which `versions` (distinct hashes) and "latest" ignore. Secret scanning happens in the drain only: on a hit the drain emits no `artifact_version`, moves the entry to `queue/rejected/` with a `.reason` (`secret: <pattern> at line N in <path>`), and the content never leaves the machine. The queue entry carries no file content.
- Non-goals: parsing shell commands to guess written paths; a repo-wide sweep; changing scanner patterns; a second scan in the shim or the server's MCP route; any post to the service from the shim or the MCP route; any spool write from the shim other than the server-requested `enqueue_file_snapshot`.

### Domain: Feedback tool (`artifact_feedback` on the server's MCP surface)

- Owns: the tool as the server defines it (Go, on the endpoint the MCP shim issue builds): description, annotations, argument validation, state set and wording, the declared context and declared local action, the decision to request the enqueue, and the report of scoring state (the source `scoring()` in `internal/serve/admin.go` reads). Nothing of this is in `yakka.py`. The tool is read-only on the service: it reads the store and answers, and never calls `ingest.Ingest`.
- Contract, argument: `path` (string), absolute or relative to the session's project directory.
- Contract, declared context (names exact; the server declares them, the shim injects them, the agent cannot supply them):

  | Parameter | Value read on the agent's machine |
  |---|---|
  | `project_dir` | the harness-supplied project directory, absent if the harness gives none |
  | `cwd` | the shim's working directory, used only to name it in an error |
  | `resolved_path` | `path` resolved against the base list the declaration gives, `["project_dir"]`; absent when `path` is relative and no base exists. `cwd` is never a base, so a path is never resolved against the plugin directory |
  | `file` | `{exists, is_file, size, mtime, content_hash, read_error}` (`read_error` is the OS error code) read at `resolved_path`. No `content` and no `scan`: the file's bytes are read only to hash them, never sent (ledger 16) |
  | `git` | `{top, rel_path, repo_id, error}` from `git rev-parse --show-toplevel`, the path relative to it, and `repo_id` by the drain's rule (normalised remote, else root commit); `error` is a code (`no_repo` or `no_commit`), not wording |
  | `queue` | `{pending: [{age_s, mtime}], rejected: [{reason, mtime}]}`, local lookup, no decision: spool and `rejected/` entries whose normalised path and repo (the drain's path function, which recognises hook writes and `artifact_snapshot` entries alike) equal `(git.repo_id, git.rel_path)`, so another repo's `docs/plans/01-x/DESIGN.md` never matches; `reason` is the drain's `.reason` text (pattern and line) |
  | `drain` | `{running}` from the `.drain.lock` probe |
  | `effects` | `[{action, ok, error}]`, present only on the forward that follows a directive; `error` is a code: `capture_off` (`YAKKA_HOOKLOG` off, so nothing was queued), `spool_dropped` (the spool printed no queue file name: unwritable queue, empty or over-long conversation ID), `yakka_bin_set` (`YAKKA_BIN` is set, so the spool would kick a drain that does not know the kind), `unsupported`. A started or absent drain is not an effect error; it shows in `drain.running` |

  Declared local action: `local_actions: ["enqueue_file_snapshot"]`. The action writes one `artifact_snapshot` entry for `resolved_path` and kicks the drain (Artifact capture domain).

- Contract, states, decided on the server from the argument, the context and the service's own data, in this order. Argument errors (relative path with no `resolved_path`: an error naming `cwd` and asking for an absolute path; `file.exists` false, `is_file` false or `read_error`: an error naming the path) are tool errors, not states. There is no `read-only key` error: the tool needs only read scope. States: `not tracked` (`git.error`, or `keys.Kind(git.rel_path)` is not design, brief or report); `delivered` (the service's latest hash for the path equals `file.content_hash`, whatever the queue holds); `rejected` (a `queue.rejected` entry with `mtime` at or after `file.mtime`, even if a newer entry is pending, which will be refused too; the line gives the pattern and line, never the match, and the fix: rewrite the file, the new write is the repair); `queued` (the service lacks the hash and a covering entry is pending, or `effects` reports the enqueue done, so the entry was there already or the shim has just added it; with no covering entry left after `effects` ok the drain has just taken it and the line says to call again; otherwise the line gives the count, oldest age and `drain.running`, says the version is on its way and to call again in a few seconds, and when no drain runs says to run `yakka status`; a covering entry older than 300 s with no drain running is answered as `not delivered` or `stale` instead, naming the age and `yakka status`, so a dead drain or a key the service refuses does not read as waiting forever); `not delivered` (the service holds no version of the path and nothing is pending, because the enqueue could not be done or the pending entry is stale: the line names the `effects` error and the fix); `stale` (the service holds an older version and nothing is pending, for the same reasons; the line names both short hashes and the `effects` error). When the service lacks the hash, nothing is pending or rejected, and no `effects` came with the call, the reply is the `enqueue_file_snapshot` directive, not a state. The server never sends the directive twice for one call. The shim's `bad config` and `unreachable` errors are not states of this tool.
- Contract, `delivered`: prints the existing `screen:` line (`pass`, `flagged: <reason>`, `unscreened`, `awaiting screen`) plus a `scoring:` line whose value `on`, `off` or `pending` the server takes from its own scoring state (scorer and checks loaded), never from the client. `pending` means received under 30 s ago; the tool waits up to 10 s for the screen before answering and says to call again. `off` says scoring is not configured on the service and that stored content will be scored by an admin rescore once it is. Where scores exist, the existing baseline comparison lines are unchanged.
- Contract, annotations: `artifact_feedback` stays read-only like `list_checks` and `search_artifacts`: `readOnlyHint` true, `idempotentHint` true. It needs read scope only, so no write-scope check is added for the MCP route (the scope check stays on `/v1/ingest`, `serve.go:640`), and the MCP route never wakes the screen worker: the drain's `/v1/ingest` call does that (`serve.go:755-758`), so the screen starts when the version arrives and the 10 s wait for a pending screen still holds. The local enqueue is not a write by the tool; it is a local effect the server asks the shim to run, onto the queue the hooks already write (ledger 22 and 24).
- Non-goals: new state names for scoring detail.

## Architectural Implications

## Decisions

- No config means an error, not local. The issue and Cody both require that nothing defaults to 8770; `mode = "local"` keeps the local workflow available.
- Final-write recovery reconciles content instead of detecting shell writes. Any shell heuristic misses some writer (formatters, editors, subprocesses); comparing current content to the service has no blind spot at the points where it is checked.
- `artifact_feedback` reconciles through the queue, not by posting (Cody, 2 Nov 2026, 11:18 PM AEST: "Maybe just don't have feedback have a 'secondary effect' of posting directly. It can push to the queue for it to be drained as normal, and if it's already on the queue or the shim queues, it can return early to tell the client it's waiting."). The tool stays read-only. When the service lacks the file's hash and the version is not already queued, the server asks the shim to queue it (directive `enqueue_file_snapshot`), the shim does and kicks the drain, and the call returns `queued` at once; the drain delivers it as it delivers everything, with its one scan. It is the point where the agent is waiting, so it closes the loop even when capture missed the write, at the cost of one repeat call. How the enqueue fits the shim rule is ledger 22. Rejected alternatives: server-side intake through `ingest.Ingest` with the file injected (needs write scope, a worker wake, `readOnlyHint` false, and a second scan in the shim to keep a secret off the wire; superseded by this decision); a direct POST from the shim (the shim only relays and injects); the shim enqueueing before every forward (a queue entry per call even when the service has the file).
- The Stop sweep is bounded to files git reports modified or untracked in the working repo, with no local "last sent" store (the service dedupes, with `ts` set to the file's mtime). Rejected alternative: a repo-wide mtime sweep.
- The Codex instruction goes in the server's MCP `instructions` and tool description, not in AGENTS.md; both load at session start without a per-project file. This assumes Codex shows server instructions (ledger 5).
- The backlog is uploaded from a staged copy, never by draining the original in place, and sends hook events only: the events are 3 to 11 days old, and building artifact versions from them would attach today's file content to old events.
- Order: config contract first, legacy retirement next (so the old queue is quiescent), final-write fix before the backlog (Cody's order), the Codex and scoring work before the end-to-end acceptance. The MCP shim issue lands before phase 3 starts; phases 1 and 2 do not wait for it.
- All MCP tool logic goes on the server, including when to queue the file and every word about it. Rejected alternative: keep the state wording and relative-path rules in the local shim and mirror them on the server (two copies, and the local one is the pattern the shim issue removes).

### Assumption 23

- Question: What exactly is enqueued, written how, and by whom?
- Answer chosen: One `artifact_snapshot` `.evt` file in the spool's form (verified in `spool.sh:42-56`: written under `<queue>/tmp/` then renamed to `<conversation_id>-<ts>-<pid>-<rand>.evt`; one envelope line `{"ts","harness","event"}` then the payload; `umask 077`), with a payload of `session_id` `feedback-<repo_id>`, `cwd` and `path`, and no content: the drain reads file content at batch time, not from the entry (`_read_file`, `yakka.py:527`, `658-668`). - Rationale: "same queue-file form the hooks/spool produce" is met by construction, and the kick comes with it. A pointer rather than a copy matches how worktree writes already reach the service and keeps content out of the queue; a file changed before the drain runs is sent in its newer form, which is what "the current version" means.
- If wrong: if Cody wants the content captured at enqueue time (a snapshot in the literal sense), the entry carries it and the drain scans and sends it; that changes the entry's payload and the drain's read, not the shim or the tool contract.

### Assumption 24

- Question: With no write scope and `readOnlyHint` true, what happens with a read-only key, and is the local enqueue consistent with a read-only annotation?
- Answer chosen: The tool answers for a read-only key (no `read-only key` error, no write-scope check on the MCP route). A read-only key cannot make the drain's `/v1/ingest` succeed (`serve.go:640`), which is the same for every hook event today; the drain's existing failure contract reports it (phase 1); the `queued` answer shows the growing oldest age and, once the oldest covering entry is over 300 s old with no drain running, becomes `not delivered` or `stale` with the `yakka status` fix. The 300 s is a default (the drain lingers and batches within seconds). The annotation describes the tool's effect on the service, which is none; the enqueue is a local effect on the queue the hooks already write, requested by the server and run by the shim, and is why Cody framed it as a secondary effect.
- Rationale: Cody's decision that the tool stays read-only with no write scope and no worker wake.
- If wrong: if a harness's permission model should treat the call as a write because of the local effect, the annotation question goes to the MCP shim issue, which owns how a tool declares local actions to a harness.

### Assumption 25

- Question: After the adversarial read, how does the tool avoid answering `queued` when the queued entry will never produce the version, or when an older entry does not cover a newer write?
- Answer chosen: Only a covering entry counts as pending: its `mtime` is at or after the file's, because a batch may have read the file before the latest write. The drain is the sole eligibility gate and moves an entry that yields no version (not UTF-8, outside the repo, not a scored kind) to `rejected/` with a reason, never a silent delete. A covering entry older than 300 s with no drain running becomes `not delivered` or `stale`. Everything the shim adds sits under one reserved key (`_local`) that it overwrites. The `queue` lookup matches on `(repo_id, rel_path)`. A second directive gets the shim's own `bad directive` error.
- Rationale: each closes a loop or a spoof the first design left open (an unbounded `queued`, an agent-supplied `file` or `queue`, another repo's same-named plan matching); all are server-side wording with generic shim mechanics, within the #177 rule as widened by ledger 22.
- If wrong: the 300 s bound is a default and moves with the drain's observed latency; the reserved key can be a prefix convention instead of one name without changing any outcome.

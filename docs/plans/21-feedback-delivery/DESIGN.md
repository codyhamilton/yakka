## Problem

An agent that writes a design and calls `artifact_feedback` has never received `delivered` with a verdict and scores, so it cannot act on a flagged check or record a pass. Each cause below was traced in the code and against live evidence; none is a single bug.

1. **The final write is invisible to capture.** The client learns a file changed only from a PostToolUse event whose `tool_name` is in a fixed write-tool set (Write, Edit, MultiEdit, apply_patch and a few aliases; `_write_tools` in `plugins/yakka/client/yakka.py`). The budget session `c70d3e4f` wrote `docs/plans/01-local-finance/DESIGN.md` three times with Edit (02:03:58-02:04:00Z), then a last time with a Bash `python3 - <<'E' ... open(p,'w')` heredoc at 02:04:06Z, the 1 s gap in the issue. The remote's hash received at 02:04:05Z is the Edit-era content. The Bash call produced a hook event but no `artifact_version`, because a shell command names no path the client can attribute. Nothing else rescued it: the commit catch-up (design 01) sends the committed blob only from a captured `git commit` tool call, and the transcript has none (commit 52435db appears between sessions), and the Stop hook at 02:04:15Z carries no paths. The remote never gets the final hash and `artifact_feedback` returns `stale`, whose message ("normally a write still in the batch window") tells the agent to wait for something that never arrives. This account is from the session transcript and is consistent with the code; the budget checkout itself was not read. The drain is sound: it reads content at batch time, has no per-write debounce, rescans after releasing its lock (no lost wake-up), and the server returns the latest version by `received_at`.
2. **Secret-scan withholding is silent unless the file is matched.** The client withholds an `artifact_version` whose content hits a pattern, for worktree writes and for the commit catch-up, and moves the queue file to `queue/rejected/` with a `.reason`. The live yakka queue holds five such files (`env_assignment` at line 40 of a brief and at line 775 of `docs/plans/91-landing-centered-dial/DESIGN.md`). A long design that trips the scanner is never delivered. This is a second way a version fails to reach the remote, with the same fix surface; the scanner's patterns are not changed here (open question 2).
3. **`delivered` does not say whether the file was scored, and the scorer state is not surfaced.** The server screens in a worker and scores only when a scorer and a checks directory are configured: no `TYPESAFE_API_KEY` yields "scorer none; verdicts are unscreened", and a key without `YAKKA_CHECKS_DIR` yields "scoring is off ... screening only" (`packages/yakka/cmd/yakka/main.go`, `runServe` startup via `screenStep`). Today the local feedback handler prints `screen: unscreened (no scorer on the service)` and `screen: awaiting screen` (`plugins/yakka/client/yakka.py`, `screen:` lines at 2129-2146), but it cannot tell the agent whether "awaiting" means seconds or never, and content stored while the scorer was off stays unscreened until an admin rescore (#169). Whether the live remote has the scorer on could not be established from this checkout and cannot be changed in this run; the service knows it (`scoring()` in `packages/yakka/internal/serve/admin.go:89-92`, today exposed only through `GET /v1/admin/status`), so the build reads it first.
4. **Codex never calls feedback, for two reasons.** The Yakka MCP is loaded in Codex (`codex mcp list` shows `yakka`, enabled, `python3 ./client/yakka.py mcp`), so loading is not the gap (the issue's "may not be loaded" is answered). First, the instruction to call feedback lives only in the design, refine and execute skills; no Codex session after the switch from the old `workflow` plugin (about 2026-10-31 08:30) read a skill or made an MCP call. The issue says Codex AGENTS.md carries the instruction; the files inspected (no `~/.codex/AGENTS.md`; the budget and garcia-music project AGENTS.md) contain no Yakka or feedback text, so the instruction as shipped does not reach Codex. Second, `.codex-mcp.json` sets `"cwd": "."`, so the server runs in the plugin cache root; the nine historic Codex calls (all to the old `mcp__workflow__` tool) failed on relative paths resolved under `~/.codex/plugins/cache/...` and, with absolute paths, returned `not delivered`. The same relative-path trap applies to the local Yakka MCP process today: it resolves a relative path against its own `os.getcwd()` and reads no harness project-directory variable or MCP roots (`yakka.py:1875-1880`, `1971-1977`). The MCP `instructions` string describes the tools and does not tell the agent when to call them.
5. **A local fallback exists in the client, and tests encode it.** `LocalEndpoint = "http://127.0.0.1:8770"` is substituted when no client config exists (`Load()` in `plugins/yakka/client/yakka.py`), and `yakka status` prints "config: none (local mode)". There is no explicit local marker, so a client with remote intent but no file fails over silently. The Oct 30 `unreachable` results came from this path, because `client.toml` did not exist until 2026-10-30 23:37 AEST; that file now exists, so this machine is safe by accident. Half-set env is already an error and no code substitutes the local endpoint after a failed request; the gap is the file-absent and no-marker cases. Python tests that assert the old behaviour (`TestMissingFile` in `test_clientconfig.py`, `test_status.py`, and any other that relies on the no-file default) will change. The Python `login` default (`https://api.yakka.build`) differs from the runtime default.
6. **A legacy process still runs, and a backlog is stranded.** pid 7649, `~/.cache/workflow/0.1.0/workflow-linux-amd64 mcp`, is the MCP child of a long-lived `codex` started by `~/.config/systemd/user/codex-usage-probe.service` (tmux server `codex-usage`, a `while :; do codex ...; sleep 15; done` loop). A successful drain deletes what it sends, so draining it in place is destructive and cannot be retried.
7. **All MCP tool logic is in the local client, and the server has no MCP endpoint.** The `# --- mcp ---` section of `yakka.py` (lines 1840-2514) holds the tool list, descriptions, schemas, `readOnlyHint` annotations, `_MCP_INSTRUCTIONS`, argument validation and every `artifact_feedback` state and wording; the Go server registers REST routes only (`internal/serve/serve.go:485-523`). Items 1, 3 and 4 each land in that section: the feedback wording, the `stale` and scoring states, the instruction text, relative-path resolution and the read-only annotation. `artifact_feedback` also reads cwd, stat and file bytes (hash), `git rev-parse --show-toplevel`, git remote or root commit (`repo_id`), a scan of the queue directory for unsent writes of the file, the drain lock, `Load()`, and starts the drain (`yakka.py:1967-2063`). A decision of 2 Nov 2026 makes the local MCP side a thin shim and puts all tool definitions and logic on the server; a separate Yakka issue, the MCP shim issue (#177), builds that (designed as Plan 24 and merged to master as a design), and this design depends on it.

## Solution Shape

After this change, a client either talks to the remote it was configured for or stops with a message; every changed design, brief or report reaches the remote whichever process wrote it, by the end of the turn at the latest (at the feedback call under E1), always through the local queue and the drain; `artifact_feedback` is read-only on the service, says whether the service holds the file's current version and, when it does not, reports the local queue facts the shim injects as read-only context; once delivered it says exactly what the service did with the file (screened and scored, scoring off, or still pending); both harnesses tell the agent to ask for feedback and Codex resolves paths correctly. The legacy source is retired and the stranded history is uploaded once through the same pipeline. Every MCP tool this plan adds or changes is defined and answered on the server; the local shim forwards the call with auth and read-only local context added and does nothing else (Plan 24, the authoritative foundation).

One behaviour Cody asked for is **not** delivered by that foundation and is held: when the file on disk is newer than anything on the queue or the service, `artifact_feedback` itself queues a snapshot instead of uploading it, answers `queued`, and the drain delivers later (Cody, 2 Nov 2026, 11:18 PM AEST; quoted under Decisions). That needs a shim-run local effect, which Plan 24 refuses to build and Cody has not approved. It is written below as the conditional extension E1 (NOT AUTHORIZED) and Phase 3 carries a partial hold on it (Assumption 26): either E1 is approved as its own versioned change, or Phase 3 takes the acceptance that relies on the hooks, the Stop sweep and the drain, in which a Bash-heredoc write made before Stop is reported as not delivered, not queued.

### Domain: Client configuration (endpoint resolution)

- Owns: deciding remote, explicit local, or a named error from env and `client.toml`; the wording of config errors; the Python client (`plugins/yakka/client/yakka.py`) as the one implementation; the `yakka status`, Python drain and MCP shim consumers of that decision (the shim takes its endpoint and bearer from `Resolve`, the one login the drain also uses).
- Contract: `Resolve` returns exactly one of `Remote{endpoint, key}`, `Local` (loopback endpoint `http://127.0.0.1:8770`, no bearer) or `Error{what, fix}`. First match wins:
  1. `YAKKA_ENDPOINT` and `YAKKA_KEY` both set: Remote with those values. `YAKKA_MODE=local` alongside either is an Error (conflicting).
  2. Exactly one of the two set: Error (`what`: which is missing; `fix`: set both or unset both). This already exists.
  3. `YAKKA_MODE=local`, neither set: Local. The env form overrides the file for processes that inherit it.
  4. `client.toml` (path `YAKKA_CLIENT_CONFIG`, else `~/.config/yakka/client.toml`) present: `mode = "local"` with no key is Local; `endpoint` and `key` both present is Remote; anything else (key without endpoint, endpoint without key, `mode = "local"` with a key, unreadable or unparseable file) is an Error naming the file and the field. The file is the primary marker because harness-spawned hook, shim and drain processes do not inherit a shell variable set only for `yakka serve`.
  5. Nothing set and no file: Error "yakka is not logged in", fix "run /yakka:login, or set YAKKA_ENDPOINT and YAKKA_KEY, or set `mode = "local"` in client.toml for a local server".
  A resolved Remote is used as configured for every request in the process; no path substitutes another endpoint on failure, partial config or absence. `127.0.0.1:8770` appears only as the Local endpoint and as the `yakka serve` bind default. Local mode is the Python drain posting over HTTP to a loopback `yakka serve` (which ignores bearer tokens, so no key is sent); no part of it relies on `yakka serve` hosting the drain.
- Failure contract: a failed remote request reports what failed (network, auth, server status) against the configured endpoint with userinfo stripped, says whether events stay queued for retry, and gives the fix (`yakka status`, `/yakka:login`, network). Hooks still spool with no network and never fail the agent. A drain whose config is an Error leaves queued files untouched and logs the error once. The shim's failure is its own error, not a tool state: when `Resolve` is an Error, or the server cannot be reached, the shim answers the forwarded request with Plan 24's own error, `bad config` or `unreachable`, whose message names what failed and gives the fix; `unreachable` also carries `queued_locally`, the count of pending queue files, which is how it says how many local writes stay queued (a `bad config` error leaves queued files untouched, as above). Those two cases stay in the shim because they are how it reaches the server; no tool wording or state lives there.
- Non-goals: the server's own `Config.Local()` (server-side local mode), the sync credential of plan 18 (it already refuses loopback), the login OAuth flow.

### Domain: MCP boundary (local shim and server surface)

Owned by Plan 24 (issue #177), merged to master as a design (PR #180, `f5a9f9e`; Plan 24 `DESIGN.md` blob `7ea38cf`, from commit `e659fd9`). Nothing in it is built or deployed. Plan 21 binds to Plan 24's names, shapes, errors and order of checks and does not restate them; where this document and Plan 24 disagree about the foundation, Plan 24 wins until an amendment to it is approved. Plan 21 phase 3 owns the handler changes for `artifact_feedback` on that foundation (Feedback tool domain), the Stop sweep, the drain and the queue matchers; phase 5 owns the one-line edit of the tool's declaration that moves the path base from `cwd` to `project_dir`. Plan 21 adds no reader, no shim code and no registry change.

- Owns: nothing of its own; the split between the local MCP shim in `yakka.py` and the MCP endpoint on the Go server is Plan 24's.
- Contract (base, Plan 24, authoritative): the server serves `POST /v1/mcp` behind the REST bearer authentication and tenant rules, with a registry that owns every tool, its description, schema, annotations, scope, timeout, instruction, declaration and handler. The shim does two things. (a) It injects auth: the bearer from the one login function the drain also uses (`Resolve` once phase 1 lands), none in explicit Local mode, and the shim never falls back from a resolved remote. (b) It fills the reserved `params.arguments._local` with the values of the fixed table of read-only readers that the tool's declaration (`_meta["yakka/tool"]` in `tools/list`: `v`, `rev`, `context`) names, and overwrites any `_local` the agent supplies. A reader that fails is injected as `{"_failed":{"code"}}`; the registry turns a failed, missing or undeclared required reader into the tool error `local context unavailable: <reader> (<code>)` before the handler runs, so a local read problem is never read as a clean state. The registry checks, in order: authentication, scope, `_rev`, `validate`, the required-reader gate, the handler. The shim holds no tool name, description, schema, instruction, validation, state or wording, runs no effect, writes nothing (no spool, no queue, no process except the readers' fixed read-only `git` argv), and does not kick the drain. The registry refuses a declaration with `local_actions` and there is no `effects` context.
- Contract (the shim's own errors, Plan 24's closed set, used by phase 1's failure contract): `bad config`, `unreachable` (with `queued_locally`, the count of pending `*.evt` files), `unauthorized`, `server unsupported`, `timeout`, `redirect refused`, `bad reply`. A failed `initialize` is one of these errors, not a synthesized result (Plan 24 ledger 6; settles this plan's open question 5).
- Stays local, unchanged by this plan: config resolution (Client configuration domain), hooks, the spool and the drain. The drain is kicked by the hooks (`spool.sh` after each spooled event, unless `YAKKA_HOOKLOG_KICK=0` or `YAKKA_HOOKLOG` is off), by Plan 24's decision D1; the shim's own kick is removed there and nothing in the base design puts a drain side effect back in the shim.
- **Conditional extension E1: a server-requested local effect (NOT AUTHORIZED, not built, not assumed).** The proposal, kept exact so that it can be approved or refused as written. A tool declaration gains `local_actions: ["enqueue_file_snapshot"]` (a declaration `v: 2`, so Plan 24's version negotiation hides the tool from an old shim). A reply to `tools/call` may carry a machine-readable directive `{action, path}` instead of an answer. If `action` is in that tool's declared list and `path` equals the `resolved_path` the call already carried, the shim runs the action, re-reads the declared context, adds an `effects` entry `{action, ok, error}` (`error` a code, never wording) to `_local`, forwards the same call once more and relays that second reply unchanged. The directive reply is never shown to the agent. At most one directive round per call; a second directive in the second reply is not run and the shim answers its own error beginning `bad directive`. An action not declared, or one the shim has no implementation for, is not run: the shim forwards once with `effects` `[{action, ok: false, error: "unsupported"}]`. The action table is fixed and has one entry, `enqueue_file_snapshot`: it writes one `artifact_snapshot` queue entry for `resolved_path` by running `spool.sh` (so the entry form, the queue directory, the `YAKKA_HOOKLOG` switch and the spool's drain kick are the spool's code), with no shell, no argument from the server beyond the path, and no file content. It needs `spool.sh` to gain an opt-in `YAKKA_SPOOL_PRINT=1` that prints the queue file name, so that queued can be told from dropped. Effect error codes: `capture_off`, `spool_dropped`, `yakka_bin_set` (a set `YAKKA_BIN` would kick a drain that does not know the kind), `unsupported`. What approval requires: Cody's decision (Assumption 26); an amendment of #177's rule from "auth and local context" to "auth, local context and one server-requested, path-bound effect"; and a separate versioned change on top of Plan 24 (declaration v2, the registry no longer refusing `local_actions` for that tool, the shim's action table and directive handling, the `spool.sh` change, which Plan 24's phase 4 asserts is byte-identical for its own change). Plan 21 does not build it, does not assume it and does not move any of it into "plumbing"; only the held clause of Phase 3 depends on it.
- Non-goals: moving `list_checks` and `search_artifacts` or building the endpoint (Plan 24); any tool logic in `yakka.py`; any write to the service by a Plan 21 MCP tool (`artifact_feedback` posts nothing, and the MCP route never carries file content).

### Domain: Artifact capture (worktree to remote)

- Owns: which file versions are sent and when; client-side secret withholding; reconciliation of local content against the remote.
- Contract: every worktree `artifact_version` for a scored-kind file in a git work tree reaches the service the one way, through the local queue and the Python drain; an upload from the MCP route does not exist. Triggers that put a file on the queue: the write-tool hook events as today; (b) below, unconditional; and (a) below, held (E1 only). The queue entry is a new kind, `artifact_snapshot`: one `.evt` file in the form the spool produces (written under `tmp/` then renamed, named `<conversation_id>-<ts>-<pid>-<rand>.evt`, one JSON envelope line `{"ts","harness","event":"artifact_snapshot"}` then a JSON payload carrying `session_id` `feedback-<repo_id>`, `cwd` (the repo top) and the file's absolute `path`). It holds a pointer, not the content: like every worktree write today, the drain reads the file at batch time (`_read_file`, `yakka.py:658-668`), so a file changed between enqueue and drain is sent in its newer form. The build's drain turns the entry into one `artifact_version` (source `worktree`, `conversation_id` `feedback-<repo_id>`, `ts` the file's mtime, a build change: today a fact's `ts` is the envelope's, the enqueue time) and no `hook_event`, through the existing scan, hash and conversation-ID rules, and the drain's path function (`_write_paths`, which Plan 24's `queue` reader also calls) recognises the kind. The drain is the sole eligibility gate: it resolves the real path before the repo and kind test, and an entry that yields no `artifact_version` (not UTF-8, outside the repo or a symlink out of it, not a scored kind, no repo identity) is moved to `queue/rejected/` with a `.reason` (`unreadable`, `not_in_repo`, `not_scored_kind`) instead of being deleted silently, so no call can loop on an entry that vanishes without a version. (b) The Stop and SessionEnd events (the Claude and Codex hook files both have them), local and in Python: for each scored-kind file that `git status --porcelain --untracked-files=all` reports modified or untracked in the session's working repo (untracked directories are expanded to files), an `artifact_snapshot` entry is written in the same form. `spool.sh` is unchanged for hooks (bash builtins, no parsing, no network, no Python); the sweep runs in `yakka.py`, either on the Stop and SessionEnd hook events the drain reads from the queue or in a hook command the plugin adds, which the build settles. The sweep is the one trigger that recovers a write no write-tool event named, and it fires at turn end, not at the agent's feedback call. It is for live events only: an event whose envelope `ts` is older than a bound (default 1 h, ledger 23) is not swept, so a drain of a staged legacy queue never turns old Stop or SessionEnd events into snapshots of today's files. (a) Held, E1 only: if E1 is approved, `artifact_feedback` may cause the shim to write the same `artifact_snapshot` entry for the call's `resolved_path` when the service lacks the file's hash and the injected `queue` shows no covering entry (a pending entry whose `mtime` is at or after `file.mtime`; an older entry may have been read by a batch before the last write) and no rejected entry at or after `file.mtime`; the call then returns `queued` at once and never waits for the drain. Without E1 no call writes the queue. No client-side "last sent" memory exists. The service's row hash covers every top-level key except `id` and `content` (`internal/keys/keys.go` `Canonical`, so `type`, `ts`, `conversation_id`, `repo_id`, `path`, `content_hash`, `source`, `harness` and `event` all count), so a repeat of unchanged content from the same conversation and mtime is answered `duplicate`; a re-touched file with the same content stores one more row, which `versions` (distinct hashes) and "latest" ignore. Secret scanning happens in the drain only: on a hit the drain emits no `artifact_version`, moves the entry to `queue/rejected/` with a `.reason` (`secret: <pattern> at line N in <path>`), and the content never leaves the machine. The queue entry carries no file content.
- Non-goals: parsing shell commands to guess written paths; a repo-wide sweep; changing scanner patterns; a second scan in the shim or the server's MCP route; any post to the service from the shim or the MCP route; any spool or queue write from the shim (E1's one action is the only candidate, and it is not authorized).

### Domain: Feedback tool (`artifact_feedback` on the server's MCP surface)

- Owns: the tool as the server defines it (Go, in Plan 24's registry): description, annotations, argument validation, state set and wording, and the report of scoring state (the source `scoring()` in `internal/serve/admin.go` reads). Nothing of this is in `yakka.py`. Plan 21 changes Plan 24's `artifact_feedback` handler by exactly the differences listed under the states below (all in phase 3 except (6), phase 5), and its declaration by the one edit in phase 5. The tool is read-only on the service: it reads the store and answers, never calls `ingest.Ingest`, never writes locally, and needs read scope only.
- Contract, argument: `path` (string), absolute or relative to the session's project directory.
- Contract, declared context: Plan 24's names and shapes, unchanged. The server declares them (`cwd` optional and the rest required, as Plan 24 ships it; `project_dir` is added at phase 5), the shim reads them with its fixed read-only readers, and the agent cannot supply them (`_local` is overwritten).

  | Parameter | Value (Plan 24 reader, v1) |
  |---|---|
  | `cwd` | `{path}`, the shim's working directory; optional, used only to name it in an error |
  | `project_dir` | a Plan 24 reader (`{path}` or `{path: null}`, the harness-supplied project directory) that Plan 24's `artifact_feedback` declaration does not list; phase 5 adds it as an optional entry, used only to word an error |
  | `resolved_path` | `{path, base}`: `path` argument normalised and, if relative, resolved against the first available base in the declaration; `path` null when the argument is not a string or is relative with no base. Plan 24 ships `bases: ["cwd"]`; phase 5 edits the declaration (adds the `project_dir` entry and sets `bases` to `["project_dir"]`, which also changes Plan 24's recorded fixtures for it) once open question 1 is answered, so that a relative path is never resolved against the plugin directory (Codex's `"cwd": "."`). Until then the tool's absolute-path behaviour is unaffected |
  | `file` | `{exists, is_file, size, mtime, content_hash, withheld, read_error}`: a SHA-256 only for a regular file inside a git work tree after `realpath`; otherwise `content_hash` is null and `withheld` is `outside_repo`, `symlink_out` or `too_large` (over 256 MiB). No content and no scan: the file's bytes are read only to hash them, never sent (ledger 16) |
  | `git` | `{repo_id, rel_path, error}`; `error` is a code (`no_repo`, `no_commit`, `git_unavailable`), a fact and not a failure. There is no `top` (Plan 24 drops it: the server needs the identity and relative path, and an absolute repository path adds egress) |

  | `drain` | `{running}` from the `.drain.lock` probe |

  There is no `effects` parameter: it exists only in E1.

- Contract, states, decided on the server from the argument, the context and the service's own data, in this order. Argument errors are tool errors, not states, and use Plan 24's texts: `path must be a non-empty string`, `arguments must be an object`, `path does not exist: <abs>`, `path is a directory, not a file: <abs>`, `cannot read <abs>`, `file too large to hash: <abs>`; a relative path with no base (`resolved_path.path` null) is an error that names `cwd` when injected and asks for an absolute path. A failed or missing required reader is Plan 24's `local context unavailable` error, never a state. There is no `read-only key` error. States: `not tracked` (`git.error` is `no_repo`, `git_unavailable` or `no_commit`, with `no_commit` worded as "no commit yet"; `file.withheld` is `outside_repo` or `symlink_out`; or `keys.Kind(git.rel_path)` is not design, brief or report); `delivered` (the service's latest hash for `(git.repo_id, git.rel_path)` (`Tenant.Artifact`, `store.go:929-938`) equals `file.content_hash`, whatever the queue holds); `rejected` (a `queue.rejected` entry with `mtime` at or after `file.mtime`, even if a newer entry is pending, which will be refused too; the line gives the pattern and line, never the match, and the fix: rewrite the file, the new write is the repair); `queued` (the service lacks the hash and a covering entry is pending: one whose `mtime` is at or after `file.mtime`; the line gives the count, oldest age and `drain.running`, says the version is on its way and to call again in a few seconds, and when no drain runs says so with Plan 24's fix, that a drain starts at the next hook event or the plugin's `bin/yakka drain` runs one; a covering entry older than 300 s, whether or not a drain runs, is answered as `not delivered` or `stale` instead, naming the age, `drain.running` and `yakka status`, so a dead drain or a key the service refuses does not read as waiting forever); `not delivered` (the service holds no version of the path and nothing covering is pending or rejected: the file has not reached the local queue, which is what a write no write-tool event named looks like before the end-of-turn sweep; the line says so and gives the fix: save the file again with the Write tool or make a real Edit, since a no-op edit may be refused and fires no event; otherwise the sweep delivers it when this turn ends, and a session killed before its Stop or SessionEnd hook runs loses the write); `stale` (the service holds an older version and nothing covering is pending or rejected, for the same reason; the line names both short hashes and gives the same fix). The tool never answers `queued` for something it did not find on the queue. The shim's own errors are not states of this tool.
- Contract, differences from Plan 24's parity table, made by phase 3 on the server handler with no shim change and listed so none is silent: (1) `delivered` takes precedence over a pending or rejected entry when the hashes match (Plan 24 keeps today's order, queued then rejected then not delivered, stale and delivered); (2) a covering entry is one at or after the file's mtime, and an older one does not count as pending; (3) the 300 s bound turns a dead-drain `queued` into `not delivered` or `stale`; (4) the 1.5 s wait for the store while a drain runs (Plan 24 D1) is dropped, `queued` is answered at once, and the only wait left is the pending-screen wait below; (5) `not delivered` and `stale` carry the fix text above; (6) the relative-path error names `cwd` and asks for an absolute path (base edit, phase 5). All other rows of Plan 24's table, including D2 and D3, are adopted as they stand.
- Contract, `delivered`: prints the existing `screen:` line (`pass`, `flagged: <reason>`, `unscreened`, `awaiting screen`) plus a `scoring:` line whose value `on`, `off` or `pending` the server takes from its own scoring state (scorer and checks loaded), never from the client. `pending` means received under 30 s ago; the tool waits up to 10 s for the screen before answering and says to call again (inside Plan 24's default 20 s `timeout_s`, which the declaration may raise). `off` says scoring is not configured on the service and that stored content will be scored by an admin rescore once it is. Where scores exist, the existing baseline comparison lines are unchanged.
- Contract, annotations: `artifact_feedback` stays read-only like `list_checks` and `search_artifacts`: `readOnlyHint` true, `idempotentHint` true, scope `read` (Plan 24 already declares it so; no write-scope check, the scope check stays on `/v1/ingest`, `serve.go:640`). The MCP route never wakes the screen worker: the drain's `/v1/ingest` call does that (`serve.go:755-758`), so the screen starts when the version arrives and the 10 s wait for a pending screen still holds.
- Held with E1 (not part of the contract above): the directive `enqueue_file_snapshot`, the `effects` context and its codes, and the `queued` answer for an entry the shim has just written. If E1 is approved, the server sends the directive instead of `not delivered` or `stale` when the service lacks the hash, nothing covering is pending or rejected and no `effects` came with the call, once per call, and after `effects` ok answers `queued` (or, with no covering entry left because the drain has just taken it, says to call again); an `effects` error word (`capture_off`, `spool_dropped`, `yakka_bin_set`, `unsupported`) goes into the `not delivered` or `stale` line with its fix.

## Decisions

- No config means an error, not local. The issue and Cody both require that nothing defaults to 8770; `mode = "local"` keeps the local workflow available.
- Final-write recovery reconciles content instead of detecting shell writes. Any shell heuristic misses some writer (formatters, editors, subprocesses); comparing current content to the service has no blind spot at the points where it is checked (the sweep at turn end; the feedback call under E1).
- `artifact_feedback` reconciles through the queue, not by posting (Cody, 2 Nov 2026, 11:18 PM AEST: "Maybe just don't have feedback have a 'secondary effect' of posting directly. It can push to the queue for it to be drained as normal, and if it's already on the queue or the shim queues, it can return early to tell the client it's waiting."). The tool stays read-only and posts nothing, and all file versions go queue, then the existing Python drain, then ingest; the MCP call carries no file content. Status of the two halves: the read-only half is adopted and built on Plan 24's foundation (the tool reports the queue facts the shim reads and says `queued` when its entry is on the queue); the half that makes the call itself put the file on the queue is Cody's stated intent but needs a shim-run effect that Plan 24 does not build and Cody has not approved, so it is held as E1 and Phase 3's partial hold, and the design does not choose Cody's tradeoff for him. Rejected alternatives: server-side intake through `ingest.Ingest` with the file injected (needs write scope, a worker wake, `readOnlyHint` false, and a second scan in the shim to keep a secret off the wire; superseded by this decision); a direct POST from the shim (forbidden: the shim only relays and injects); the shim enqueueing before every forward (a queue entry per call even when the service has the file).
- The Stop sweep is bounded to files git reports modified or untracked in the working repo, with no local "last sent" store (the service dedupes, with `ts` set to the file's mtime). Rejected alternative: a repo-wide mtime sweep.
- The Codex instruction goes in the server's MCP `instructions` and tool description, not in AGENTS.md; both load at session start without a per-project file. This assumes Codex shows server instructions (ledger 5).
- The backlog is uploaded from a staged copy, never by draining the original in place, and sends hook events only: the events are 3 to 11 days old, and building artifact versions from them would attach today's file content to old events.
- Order: config contract first, legacy retirement next (so the old queue is quiescent), final-write fix before the backlog (Cody's order), the Codex and scoring work before the end-to-end acceptance. Plan 24's server phases and shim land before Plan 21 phase 3 can close; phases 1 and 2 do not wait for it.
- All MCP tool logic goes on the server, including every word about the queue. Rejected alternative: keep the state wording and relative-path rules in the local shim and mirror them on the server (two copies, and the local one is the pattern Plan 24 removes).

### Assumption 23

- Question: What exactly is enqueued, written how, and by whom?

## Problem

An agent that writes a design and calls `artifact_feedback` has never received `delivered` with a verdict and scores, so it cannot act on a flagged check or record a pass. Each cause below was traced in the code and against live evidence; none is a single bug.

1. **The final write is invisible to capture.** The client learns a file changed only from a PostToolUse event whose `tool_name` is in a fixed write-tool set (Write, Edit, MultiEdit, apply_patch and a few aliases; `_write_tools` in `plugins/yakka/client/yakka.py`). The budget session `c70d3e4f` wrote `docs/plans/01-local-finance/DESIGN.md` three times with Edit (02:03:58-02:04:00Z), then a last time with a Bash `python3 - <<'E' ... open(p,'w')` heredoc at 02:04:06Z, the 1 s gap in the issue. The remote's hash received at 02:04:05Z is the Edit-era content. The Bash call produced a hook event but no `artifact_version`, because a shell command names no path the client can attribute. Nothing else rescued it: the commit catch-up (design 01) sends the committed blob only from a captured `git commit` tool call, and the transcript has none (commit 52435db appears between sessions), and the Stop hook at 02:04:15Z carries no paths. The remote never gets the final hash and `artifact_feedback` returns `stale`, whose message ("normally a write still in the batch window") tells the agent to wait for something that never arrives. This account is from the session transcript and is consistent with the code; the budget checkout itself was not read. The drain is sound: it reads content at batch time, has no per-write debounce, rescans after releasing its lock (no lost wake-up), and the server returns the latest version by `received_at`.
2. **Secret-scan withholding is silent unless the file is matched.** The client withholds an `artifact_version` whose content hits a pattern, for worktree writes and for the commit catch-up, and moves the queue file to `queue/rejected/` with a `.reason`. The live yakka queue holds five such files (`env_assignment` at line 40 of a brief and at line 775 of `docs/plans/91-landing-centered-dial/DESIGN.md`). A long design that trips the scanner is never delivered. This is a second way a version fails to reach the remote, with the same fix surface; the scanner's patterns are not changed here (open question 2).
3. **`delivered` does not say whether the file was scored, and the scorer state is not surfaced.** The server screens in a worker and scores only when a scorer and a checks directory are configured: no `TYPESAFE_API_KEY` yields "scorer none; verdicts are unscreened", and a key without `YAKKA_CHECKS_DIR` yields "scoring is off ... screening only" (`packages/yakka/cmd/yakka/main.go`, `runServe` startup via `screenStep`). Today the local feedback handler prints `screen: unscreened (no scorer on the service)` and `screen: awaiting screen` (`plugins/yakka/client/yakka.py`, `screen:` lines at 2129-2146), but it cannot tell the agent whether "awaiting" means seconds or never, and content stored while the scorer was off stays unscreened until an admin rescore (#169). Whether the live remote has the scorer on could not be established from this checkout and cannot be changed in this run; the service knows it (`scoring()` in `packages/yakka/internal/serve/admin.go:89-92`, today exposed only through `GET /v1/admin/status`), so the build reads it first.
4. **Codex never calls feedback, for two reasons.** The Yakka MCP is loaded in Codex (`codex mcp list` shows `yakka`, enabled, `python3 ./client/yakka.py mcp`), so loading is not the gap (the issue's "may not be loaded" is answered). The issue says Codex AGENTS.md carries the instruction; the files inspected (no `~/.codex/AGENTS.md`; the budget and garcia-music project AGENTS.md) contain no Yakka or feedback text, so the instruction as shipped does not reach Codex. Second, `.codex-mcp.json` sets `"cwd": "."`, so the server runs in the plugin cache root; the nine historic Codex calls (all to the old `mcp__workflow__` tool) failed on relative paths resolved under `~/.codex/plugins/cache/...` and, with absolute paths, returned `not delivered`. The MCP `instructions` string describes the tools and does not tell the agent when to call them.

There is no explicit local marker, so a client with remote intent but no file fails over silently. The Oct 30 `unreachable` results came from this path, because `client.toml` did not exist until 2026-10-30 23:37 AEST; that file now exists, so this machine is safe by accident. Half-set env is already an error and no code substitutes the local endpoint after a failed request; the gap is the file-absent and no-marker cases. Python tests that assert the old behaviour (`TestMissingFile` in `test_clientconfig.py`, `test_status.py`, and any other that relies on the no-file default) will change. ## Solution Shape

After this change, a client either talks to the remote it was configured for or stops with a message; every changed design, brief or report reaches the remote whichever process wrote it, by the end of the turn at the latest (at the feedback call under E1), always through the local queue and the drain; `artifact_feedback` is read-only on the service, says whether the service holds the file's current version and, when it does not, reports the local queue facts the shim injects as read-only context; once delivered it says exactly what the service did with the file (screened and scored, scoring off, or still pending); both harnesses tell the agent to ask for feedback and Codex resolves paths correctly. The legacy source is retired and the stranded history is uploaded once through the same pipeline. Every MCP tool this plan adds or changes is defined and answered on the server. The local shim forwards with auth and declared read-only context; under the approved Plan 24 v2 extension it may additionally perform only the declared, reviewed-file-bound enqueue and one continuation.

The auth/context-only v1 foundation does not deliver the pre-Stop Bash-heredoc case.
The bounded approval above now authorizes E1 to meet it: when the server lacks the current hash
and no covering/rejected entry exists, the server requests the one guarded enqueue, then words
the result from effect facts and refreshed context. Phase 3 Part 2 selects A and still requires
E1 implementation and verification; this amendment performs neither. Unsupported old clients
remain visibly `not delivered` or `stale`, with no false queued/delivered claim.

### Domain: Client configuration (endpoint resolution)

- Owns: deciding remote, explicit local, or a named error from env and `client.toml`; the wording of config errors; the Python client (`plugins/yakka/client/yakka.py`) as the one implementation; the `yakka status`, Python drain and MCP shim consumers of that decision (the shim takes its endpoint and bearer from `Resolve`, the one login the drain also uses).
- Contract: `Resolve` returns exactly one of `Remote{endpoint, key}`, `Local` (loopback endpoint `http://127.0.0.1:8770`, no bearer) or `Error{what, fix}`. First match wins:
  1. `YAKKA_ENDPOINT` and `YAKKA_KEY` both set: Remote with those values. `YAKKA_MODE=local` alongside either is an Error (conflicting).
  2. Exactly one of the two set: Error (`what`: which is missing; `fix`: set both or unset both). This already exists.
  3. `YAKKA_MODE=local`, neither set: Local. The env form overrides the file for processes that inherit it.
  4. `client.toml` (path `YAKKA_CLIENT_CONFIG`, else `~/.config/yakka/client.toml`) present: `mode = "local"` with no key is Local; `endpoint` and `key` both present is Remote; anything else (key without endpoint, endpoint without key, `mode = "local"` with a key, unreadable or unparseable file) is an Error naming the file and the field. The file is the primary marker because harness-spawned hook, shim and drain processes do not inherit a shell variable set only for `yakka serve`.
  5. Nothing set and no file: Error "yakka is not logged in", fix "run /yakka:login, or set YAKKA_ENDPOINT and YAKKA_KEY, or set `mode = "local"` in client.toml for a local server".
  A resolved Remote is used as configured for every request in the process; no path substitutes another endpoint on failure, partial config or absence. `127.0.0.1:8770` appears only as the Local endpoint and as the `yakka serve` bind default. Local mode is the Python drain posting over HTTP to a loopback `yakka serve` (which ignores bearer tokens, so no key is sent); no part of it relies on `yakka serve` hosting the drain.
- Failure contract: a failed remote request reports what failed (network, auth, server status) against the configured endpoint with userinfo stripped, says whether events stay queued for retry, and gives the fix (`yakka status`, `/yakka:login`, network). Hooks still spool with no network and never fail the agent. A drain whose config is an Error leaves queued files untouched and logs the error once. The shim's failure is its own error, not a tool state: when `Resolve` is an Error, or the server cannot be reached, the shim answers the forwarded request with Plan 24's own error, `bad config` or `unreachable`, whose message names what failed and gives the fix; `unreachable` also carries `queued_locally`, the count of pending queue files, which is how it says how many local writes stay queued (a `bad config` error leaves queued files untouched, as above). Those two cases stay in the shim because they are how it reaches the server; no tool wording or state lives there.
- Non-goals: the server's own `Config.Local()` (server-side local mode), the sync credential of plan 18 (it already refuses loopback), the login OAuth flow.

- Contract (base v1, Plan 24; the bounded v2 addendum is the only exception): the server serves `POST /v1/mcp` behind the REST bearer authentication and tenant rules, with a registry that owns every tool, its description, schema, annotations, scope, timeout, instruction, declaration and handler. The shim does two things. (a) It injects auth: the bearer from the one login function the drain also uses (`Resolve` once phase 1 lands), none in explicit Local mode, and the shim never falls back from a resolved remote. The shim holds no tool name, description, schema, instruction, validation, state or wording, runs no effect, writes nothing (no spool, no queue, no process except the readers' fixed read-only `git` argv), and does not kick the drain. The registry refuses a declaration with `local_actions` and there is no `effects` context.

### Domain: Artifact capture (worktree to remote)

- Owns: which file versions are sent and when; client-side secret withholding; reconciliation of local content against the remote.
- Contract: every worktree `artifact_version` for a scored-kind file in a git work tree reaches the service the one way, through the local queue and the Python drain; an upload from the MCP route does not exist. Triggers that put a file on the queue: the write-tool hook events as today; (b) below, unconditional; and (a) below, under approved E1 once implemented. The queue entry is a new kind, `artifact_snapshot`: one `.evt` file in the form the spool produces (written under `tmp/` then renamed, named `<conversation_id>-<ts>-<pid>-<rand>.evt`, one JSON envelope line `{"ts","harness","event":"artifact_snapshot"}` then a JSON payload carrying `session_id` `feedback-<repo_id>`, `cwd` (the repo top) and the file's absolute `path`). It holds a pointer, not the content: like every worktree write today, the drain reads the file at batch time (`_read_file`, `yakka.py:658-668`), so a file changed between enqueue and drain is sent in its newer form. The build's drain turns the entry into one `artifact_version` (source `worktree`, `conversation_id` `feedback-<repo_id>`, `ts` the file's mtime, a build change: today a fact's `ts` is the envelope's, the enqueue time) and no `hook_event`, through the existing scan, hash and conversation-ID rules, and the drain's path function (`_write_paths`, which Plan 24's `queue` reader also calls) recognises the kind. The drain is the sole eligibility gate: it resolves the real path before the repo and kind test, and an entry that yields no `artifact_version` (not UTF-8, outside the repo or a symlink out of it, not a scored kind, no repo identity) is moved to `queue/rejected/` with a `.reason` (`unreadable`, `not_in_repo`, `not_scored_kind`) instead of being deleted silently, so no call can loop on an entry that vanishes without a version. (b) The Stop and SessionEnd events (the Claude and Codex hook files both have them), local and in Python: for each scored-kind file that `git status --porcelain --untracked-files=all` reports modified or untracked in the session's working repo (untracked directories are expanded to files), an `artifact_snapshot` entry is written in the same form. `spool.sh` is unchanged for hooks (bash builtins, no parsing, no network, no Python); the sweep runs in `yakka.py`, either on the Stop and SessionEnd hook events the drain reads from the queue or in a hook command the plugin adds, which the build settles. The sweep is the one trigger that recovers a write no write-tool event named, and it fires at turn end, not at the agent's feedback call. It is for live events only: an event whose envelope `ts` is older than a bound (default 1 h, ledger 23) is not swept, so a drain of a staged legacy queue never turns old Stop or SessionEnd events into snapshots of today's files. (a) Approved E1, after its implementation and verification: `artifact_feedback` may cause the shim to write the same `artifact_snapshot` entry for the call's `resolved_path` when the service lacks the file's hash and the injected `queue` shows no covering entry (a pending entry whose `mtime` is at or after `file.mtime`; an older entry may have been read by a batch before the last write) and no rejected entry at or after `file.mtime`; the call never waits for the drain; its final state follows the Feedback tool rules below, requiring refreshed covering evidence for `queued`, a matching service hash for `delivered`, and visible unconfirmed delivery or failure otherwise. Without negotiated E1 no call writes the queue; unsupported delivery remains visible. No client-side "last sent" memory exists. The service's row hash covers every top-level key except `id` and `content` (`internal/keys/keys.go` `Canonical`, so `type`, `ts`, `conversation_id`, `repo_id`, `path`, `content_hash`, `source`, `harness` and `event` all count), so a repeat of unchanged content from the same conversation and mtime is answered `duplicate`; a re-touched file with the same content stores one more row, which `versions` (distinct hashes) and "latest" ignore. Secret scanning happens in the drain only: on a hit the drain emits no `artifact_version`, moves the entry to `queue/rejected/` with a `.reason` (`secret: <pattern> at line N in <path>`), and the content never leaves the machine. The queue entry carries no file content.
- Non-goals: parsing shell commands to guess written paths; a repo-wide sweep; changing scanner patterns; a second scan in the shim or the server's MCP route; any post to the service from the shim or the MCP route; any spool or queue write from the shim beyond E1's one approved, guarded pointer enqueue.

- Contract, states, decided on the server from the argument, the context and the service's own data, in this order. Argument errors are tool errors, not states, and use Plan 24's texts: `path must be a non-empty string`, `arguments must be an object`, `path does not exist: <abs>`, `path is a directory, not a file: <abs>`, `cannot read <abs>`, `file too large to hash: <abs>`; a relative path with no base (`resolved_path.path` null) is an error that names `cwd` when injected and asks for an absolute path. A failed or missing required reader is Plan 24's `local context unavailable` error, never a state. There is no `read-only key` error. States: `not tracked` (`git.error` is `no_repo`, `git_unavailable` or `no_commit`, with `no_commit` worded as "no commit yet"; `file.withheld` is `outside_repo` or `symlink_out`; or `keys.Kind(git.rel_path)` is not design, brief or report); `delivered` (the service's latest hash for `(git.repo_id, git.rel_path)` (`Tenant.Artifact`, `store.go:929-938`) equals `file.content_hash`, whatever the queue holds); `rejected` (a `queue.rejected` entry with `mtime` at or after `file.mtime`, even if a newer entry is pending, which will be refused too; the line gives the pattern and line, never the match, and the fix: rewrite the file, the new write is the repair); `queued` (the service lacks the hash and a covering entry is pending: one whose `mtime` is at or after `file.mtime`; the line gives the count, oldest age and `drain.running`, says the version is on its way and to call again in a few seconds, and when no drain runs says so with Plan 24's fix, that a drain starts at the next hook event or the plugin's `bin/yakka drain` runs one; a covering entry older than 300 s, whether or not a drain runs, is answered as `not delivered` or `stale` instead, naming the age, `drain.running` and `yakka status`, so a dead drain or a key the service refuses does not read as waiting forever); `not delivered` (the service holds no version of the path and nothing covering is pending or rejected: the file has not reached the local queue, which is what a write no write-tool event named looks like before the end-of-turn sweep; the line says so and gives the fix: save the file again with the Write tool or make a real Edit, since a no-op edit may be refused and fires no event; otherwise the sweep delivers it when this turn ends, and a session killed before its Stop or SessionEnd hook runs loses the write); `stale` (the service holds an older version and nothing covering is pending or rejected, for the same reason; the line names both short hashes and gives the same fix). The tool never answers `queued` for something it did not find on the queue. The shim's own errors are not states of this tool.
- Contract, differences from Plan 24's parity table, made by phase 3 on the server handler; the generic E1 shim change belongs to Plan 24 and listed so none is silent: (1) `delivered` takes precedence over a pending or rejected entry when the hashes match (Plan 24 keeps today's order, queued then rejected then not delivered, stale and delivered); (2) a covering entry is one at or after the file's mtime, and an older one does not count as pending; (3) the 300 s bound turns a dead-drain `queued` into `not delivered` or `stale`; (4) the 1.5 s wait for the store while a drain runs (Plan 24 D1) is dropped, `queued` is answered at once, and the only wait left is the pending-screen wait below; (5) `not delivered` and `stale` carry the fix text above; (6) the relative-path error names `cwd` and asks for an absolute path (base edit, phase 5). All other rows of Plan 24's table, including D2 and D3, are adopted as they stand.
- Contract, `delivered`: prints the existing `screen:` line (`pass`, `flagged: <reason>`, `unscreened`, `awaiting screen`) plus a `scoring:` line whose value `on`, `off` or `pending` the server takes from its own scoring state (scorer and checks loaded), never from the client. `pending` means received under 30 s ago; the tool waits up to 10 s for the screen before answering and says to call again (inside Plan 24's default 20 s `timeout_s`, which the declaration may raise). `off` says scoring is not configured on the service and that stored content will be scored by an admin rescore once it is. Where scores exist, the existing baseline comparison lines are unchanged.
- Contract, annotations: `artifact_feedback` stays read-only like `list_checks` and `search_artifacts`: `readOnlyHint` true, `idempotentHint` true, scope `read` (Plan 24 already declares it so; no write-scope check, the scope check stays on `/v1/ingest`, `serve.go:640`). The MCP route never wakes the screen worker: the drain's `/v1/ingest` call does that (`serve.go:755-758`), so the screen starts when the version arrives and the 10 s wait for a pending screen still holds.
- Approved E1 behavior, implemented by P3 only after Plan 24's extension is verified: when
  the service lacks the hash, nothing covering is pending or rejected, and no effect result has
  been supplied, send the one bound directive. After the continuation, re-evaluate current hash,
  rejection, coverage and age before wording the answer. A successful `enqueued` or `covered`
  fact is not proof of delivery; `queued` requires refreshed covering queue evidence. If the
  drain has already taken the pointer but the service lacks the hash, answer `not delivered` or
  `stale` with enqueue acknowledged/delivery unconfirmed and the repeat-read fix. An effect

## Decisions

- No config means an error, not local. The issue and Cody both require that nothing defaults to 8770; `mode = "local"` keeps the local workflow available.
- Final-write recovery reconciles content instead of detecting shell writes. Any shell heuristic misses some writer (formatters, editors, subprocesses); comparing current content to the service has no blind spot at the points where it is checked (the sweep at turn end; the feedback call under E1).
- `artifact_feedback` reconciles through the queue, not by posting (Cody, 2 Nov 2026, 11:18 PM AEST: "Maybe just don't have feedback have a 'secondary effect' of posting directly. It can push to the queue for it to be drained as normal, and if it's already on the queue or the shim queues, it can return early to tell the client it's waiting."). The tool stays read-only and posts nothing, and all file versions go queue, then the existing Python drain, then ingest; the MCP call carries no file content. The read-only service behavior is retained. The 7 Nov 2026, 7:22 PM AEST approval above now selects the bounded queue effect as separately versioned E1, requiring Plan 24 extension implementation/verification and Plan 21 P3 handler acceptance; no implementation or deployment is claimed by this amendment. Rejected alternatives: server-side intake through `ingest.Ingest` with the file injected (needs write scope, a worker wake, `readOnlyHint` false, and a second scan in the shim to keep a secret off the wire; superseded by this decision); a direct POST from the shim (forbidden: the shim only relays and injects); the shim enqueueing before every forward (a queue entry per call even when the service has the file).
- The Stop sweep is bounded to files git reports modified or untracked in the working repo, with no local "last sent" store (the service dedupes, with `ts` set to the file's mtime). Rejected alternative: a repo-wide mtime sweep.
- The Codex instruction goes in the server's MCP `instructions` and tool description, not in AGENTS.md; both load at session start without a per-project file. This assumes Codex shows server instructions (ledger 5).
- The backlog is uploaded from a staged copy, never by draining the original in place, and sends hook events only: the events are 3 to 11 days old, and building artifact versions from them would attach today's file content to old events.
- Order: config contract first, legacy retirement next (so the old queue is quiescent), final-write fix before the backlog (Cody's order), the Codex and scoring work before the end-to-end acceptance. Plan 24's server phases and shim land before Plan 21 phase 3 can close; phases 1 and 2 do not wait for it.
- All MCP tool logic goes on the server, including every word about the queue. Rejected alternative: keep the state wording and relative-path rules in the local shim and mirror them on the server (two copies, and the local one is the pattern Plan 24 removes).
